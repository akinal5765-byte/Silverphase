## 1. 信息架构

### 1.1 区域

窗口分成六个区域,每个区域有且只有一类职责:

| 区域 | 只管 | 绝不放 |
|---|---|---|
| 菜单栏 | 帧级动作、视图状态、快捷键 | 影响渲染的数值 |
| 顶栏(工具栏) | 文件动作、视图状态、工具、两侧栏折叠 | 渲染参数 |
| 左栏(**预设**) | 胶片与相纸的选择(资源) | 参数微调、文件动作 |
| 画布 | 图像、只读叠加层、拾取类工具、直接操作 | 可编辑参数、一次性动作按钮 |
| 右栏(**参数**) | 影响渲染的参数 | 资源选择、文件动作 |
| 底栏(胶片条) | 选帧、单帧动作 | 参数 |
| 导出页 / 设置页 | 导出设置 / 应用偏好 | 单帧参数(只读回显可以) |

**用词先钉死**,不要再用"检查器"这个词:缩略图是**胶片条**(底栏),参数是**参数栏**
(右栏),胶片与相纸列表是**预设栏**(左栏)。

**布局与 Lightroom Classic 一致**:左预设、中画布、右参数、底胶片条。理由不是模仿,
是分工 —— 选一款胶片是"换一套配方",调一个滑杆是"改这套配方",两者是不同的动作,
放在不同的栏里,用户就不用在一个长栏里找东西。现在的代码把两者塞在同一个左栏,
这正是"按钮位置没有逻辑"的来源。

### 1.2 一个控件只有一个家

| 控件 | 归属 | 理由 |
|---|---|---|
| 胶片 / 相纸的选择(换配方) | 左栏(预设) | 这是"换一套",不是"改一处" |
| 滑杆、开关、下拉(改渲染) | 右栏(参数)对应分区 | 分区就是物理流程的一段 |
| 只读数值、状态徽章、直方图 | 画布叠加层(右上角) | 不是可操作的东西 |
| 分区级重置 | 该分区标题栏的 •••,文案写明作用范围 | 标题栏的动作作用于标题栏这一区 |
| 帧级重置、复制/粘贴设置 | 菜单栏 Frame | 跨分区的动作没有归属区 |
| 视图状态 | 顶栏;**菜单栏也有同一动作**,这是允许的例外 | 菜单是快捷键的可发现形式 |
| 解释性文字 | 该控件的 `.help(...)` | 不占版面 |

### 1.3 六条硬禁止

1. 同一控制不在两处(§1.2 最后一行除外)。
2. 画布上不放可编辑控件,也不放一次性动作按钮。
3. 文案里不写死配置名或 ID。
4. 新控件不许用 token 之外的字面量。
5. 不许有"只在默认值下才存在"的控件:任何会被持久化的设置都要能被找到、能改回。
6. 不许出现没有原因的禁用态。

### 1.4 骨架

```
┌──────────────┬──────────────────────────────┬──────────────┐
│ 顶栏  打开·导出 │   缩放 · 适合 · 对比 · 全屏     │ 叠加层 · 折叠 │
├──────────────┼──────────────────────────────┼──────────────┤
│ 预设栏(左)    │  画布                          │ 参数栏(右)    │
│  胶片列表      │   右上角: 直方图(只读)          │  输入 / 拍摄  │
│  相纸列表      │   其下:   徽章                 │  胶片         │
│              │                              │  显影         │
│              │                              │  彩色放大     │
│              │                              │  扫描 / 输出  │
│              │                              │  裁剪         │
├──────────────┴──────────────────────────────┴──────────────┤
│ 胶片条                                                       │
└────────────────────────────────────────────────────────────┘
```

分区内容(每个参数只有一个家,全部在**右栏**):

| 分区 | 内容 |
|---|---|
| 输入 / 拍摄 | 测光模式、曝光补偿、白平衡(色温 / 色调)、镜头校正、拍摄柔光(柔光强度 / 扩散范围) |
| 胶片 | 胶片规格(尺寸基准 / 基准尺寸)、颗粒(颗粒尺度)、胶片光晕(档位 + 光晕强度) |
| 显影 | 显影反差、DIR 效应 |
| 彩色放大 | 放大曝光、相纸反差、黄滤色（Y）、品红滤色（M）、相纸预闪、柔光放大(柔光强度 / 扩散范围) |
| 扫描 / 输出 | 相纸眩光、高光层次展开 |
| 裁剪 | 宽高比、拉直、旋转、翻转 |

**左栏只有选择,没有数值**:两款列表(胶片、相纸)属于左栏;选中之后这款胶片的**参数**
属于右栏。同一个胶片既在左栏(被选中)又在右栏(参数)出现是正常的 —— 那是两个不同的
动作,不是"同一控制两处"。

**放大机区删除**(不只是 flag 关掉):放大曝光与黄/品红滤色已经在「彩色放大」区有家。
将来若要暴露光源,它是「彩色放大」区里的一行,不是新分区。

## 2. 设计语言与材质

### 2.1 密度与节奏

- 一个控件一行。行高、控件高、行间距一律取 `Theme.Metric`,不在 View 里写数字。
- 分区内行与行**等距**;分区之间靠 hairline + `sectionBottom` 分隔。
- 参数区的目标是"一屏读完一个分区",不是"每行都很大"。宁可行短、间距准。
- **不给控件加内边距来"透气"**;透气靠行间距。控件高就是控件高。

### 2.2 表面:只有五层

实底内容表面 = **填充 + 内描边 + 顶部高光 +(可选)落影 + 圆角**。持续浮在内容之上的
导航与工具表面使用系统 Liquid Glass;模态弹窗优先使用系统呈现。光学效果由系统提供,
不能用上述实底五件套冒充。
两者仍沿用同一套字体、间距、控件和语义颜色。

| 层 | 名称 | 用在哪 | 圆角 |
|---|---|---|---|
| L0 | ground | 窗口底 | 0 |
| L1 | card | 两侧栏、胶片条 | 0 |
| L2 | well | 列表、直方图的凹槽 | 小 |
| L3 | control | 药丸、字段、按钮、滑杆轨道 | 控件圆角 |
| L4 | overlay | 浮动导航、检查器使用系统 Liquid Glass;模态弹窗沿用系统呈现 | 只有这层可有较大圆角与落影 |

规则:

- 每层比它下面一层亮或暗**一个固定步长**;步长写进 `Theme`,不在 View 里调。
- 控件使用平整填充与统一细边界;不再用上亮下暗描边模拟凸起或凹陷。边界取 `Theme.controlStroke`。
- **L0–L3 一律不投影。** 落影只属于 L4。
- 控件实底不使用垂直渐变、顶光或纹理。浮动导航与工具层按 §2.2.1 使用原生液态玻璃;模态弹窗沿用系统呈现,不用手工模糊或渐变模拟。

`Theme` 集中维护填充、边界、hover / pressed、轨道两段色和滑块样式 token。**这些值只存在于 `Theme`,View 里不许出现数字或即席色。**

### 2.2.1 液态玻璃的归属与实现（2026-10-01）

Liquid Glass 用于持续浮在照片和内容之上的导航、控制层。**顶栏、浮动工具面板和检查器
外壳保留玻璃**。模态弹窗是单独的任务呈现,优先沿用系统 sheet 的材质与行为,不要求
明显透出背景,也不为追求透图改用自定义透明面板。照片、缩略图、长文本和数据列表
本身是内容,保持原来的渲染和清晰表面。**不要为了玻璃而改变照片像素或色彩管理。**

| 表面 | 材质与归属 |
|---|---|
| 顶栏、浮动工具面板、检查器外壳 | 保留共享 `EditorChromeSurface`;macOS 26+ 为 `.glassEffect(.regular, in:)` |
| 复制设置等模态弹窗 | 原生 SwiftUI `.sheet`,保留系统背景和模态行为;不额外添加自绘玻璃外壳 |
| 纯照片导航条、画布照片、网格缩略图 | 内容本身不加玻璃;外壳需要浮层时才应用 |
| 设置窗口、复制设置弹窗的外壳背景 | 系统窗口 / sheet 表面;不额外覆盖 `Theme.cardFill` 渐变或专用底色 |
| 内容区内的长文本、许可正文、表格 | 保持 `Theme.card` / `Theme.well` 等内容表面;不把整页做成玻璃 |
| 系统菜单和原生呈现外壳 | 先沿用系统材质;自绘外壳时只保留一层背景所有者 |
| 浮层内部的按钮、复选框、字段 | 继续使用共享控件与 `.surface` / `.primarySurface`;不在玻璃父层里再叠一块玻璃 |

实现要求:

- `glassEffect` 放在内容完成布局、内边距和尺寸之后,形状使用 `Theme.Metric` 圆角。
  普通操作外壳用 `.regular`;不用 `.clear` 变体来追求过度透明。
- 模态弹窗优先保留系统呈现。macOS 的 SwiftUI `.sheet` 不支持透明背景;
  `.presentationBackground(.clear)` 不会使它透图,这不是需要绕过的渲染缺陷。
  不为了材质替换成透明 `NSPanel`,不修改 SwiftUI 私有视图层级。
  内容里也不加不透明自绘背景或额外 `glassEffect` 去替换系统外壳。
- Liquid Glass 不等于高度透明。文字较多的弹出组件适合 `regular` 变体,系统会调节
  模糊、亮度与透明度来保证可读性。不能仅凭“看起来像实底”判断材质实现失败。
- 背景只保留两类语义:系统窗口/sheet 表面,以及浮动导航/工具的系统 regular 玻璃。
  设置页不另外画 `Theme.cardFill` 渐变;复制弹窗不覆盖系统背景。两者继续使用相同的
  深色外观、文字和控件角色,不形成第三套窗口底色。
- **顶栏、检查器和工具面板必须使用同一套背景与文字对比度规则**。共用
  `EditorChromeSurface`,不把顶栏做成更透明的玻璃、面板做成另一种厚重材质。
  两者只因形状不同而选择平直底边或圆角外壳。
- `regular` 玻璃统一使用 `Theme.chromeBacking` 深色可读性衬底、`Theme.chromeEdge`
  边缘及同一套 `Theme.Ink`。衬底取回此前使用的强度,不允许各处单独调透明度或 tint。
  这是 Silverphase 面向亮照片和密集控件的产品取舍,不是 Apple 对 regular 玻璃规定的数值,
  也不是将 clear 玻璃的暗化建议直接套用。玻璃外壳和读取对比度两者都要保留。
- `Theme.Ink.tertiary` 是需要读懂的说明和刻度,不能为了弱化层级而低到不可读。
  它与顶栏、工具面板共用同一 token;依靠墨色层级区分重要性,不逐处更换字体或灰度。
- 减少透明度时,顶栏与工具面板共同使用 `Theme.windowSurface`(系统窗口背景色);
  旧系统共同使用 `.regularMaterial` 和同一可读性衬底。
  内容区域、图表、字段仍保留自己的层次,不把“背景统一”理解为抹平所有内容对比。
- `interactive()` 只用于实际可交互的独立玻璃控件;整块静态弹窗背景不使用。
  多个需要合并或变形的同级玻璃元素才使用 `GlassEffectContainer`,不为单一外壳额外包容器。
- macOS 26 以下使用系统 `.regularMaterial` 降级;开启“减少透明度”时使用实底和边界。
  浮动工具层的两条降级路径由 `EditorChromeSurface` 处理;原生弹窗由系统处理,不影响按钮、键盘和选择状态。
- 保持一屏一个主动作。短操作弹窗先呈现标题和来源,再呈现选项,底部是取消与确认。
  不把右栏长标签/远端开关布局直接复制进弹窗。复制弹窗标题取 `Font.railTitle`,
  来源句取 `Font.caption`,“选择设置”取 `Font.modernSectionTitle`;“全选 | 清除”用
  `Font.label` 的轻量文字操作,放在选项标题行右侧。字号来自角色,不按参考图目测放大。

复选框有两种**语义布局**,视觉形状仍共用 `CheckBox`:
参数启用行继续按 §2.16d 标签左、开关右;复制设置等多项选择弹窗则方框紧贴标签左侧,
可按两列紧凑排列。两者都要求点文字能切换,并提供可读的标签与选择状态。

依据: [Apple — Materials](https://developer.apple.com/design/human-interface-guidelines/materials)、
[Apple — Applying Liquid Glass to custom views](https://developer.apple.com/documentation/swiftui/applying-liquid-glass-to-custom-views)、
[Apple — Adopting Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass)、
[Apple — presentationBackground(_:)](https://developer.apple.com/documentation/swiftui/view/presentationbackground(_:))
(macOS sheet 不支持透明)。
以上表面归属和弹窗布局是 Silverphase 的产品规则;Apple 文档提供原生 API 与设计基础。

### 2.2.2 中性画布与现代控件（2026-10-01）

- 画布照片之外的空白采用固定、不透明的中性 sRGB `#303030` (`canvasSurround`)。
  与深色系统窗口/sheet 同属中性灰背景家族;不读取壁纸 tint,也不强行覆盖系统窗口色。
  窗口底、空画布、导出预览底、Metal clear 和 letterbox 共用同一来源。
  Metal drawable 使用经工作空间重新编码的值;AppKit 使用 sRGB 原值,见 §11.4。
- 菜单与数字字段使用同一圆角矩形和平整填充,菜单保留右侧展开标记。
  操作按钮继续用胶囊。所有控件共用状态 token,不为单个面板增添玻璃或凸起渐变。
- 复选框关闭时为浅细边界与暗填充,开启时为纯 accent 加明确勾号;
  不用仅有颜色的方块表达选择。尺寸、勾号、圆角取 `Theme.Metric`,
  保留 §2.16d 的可见边缘对齐和独立命中区。
- 滑杆保留简洁轨道、零点、双向有效区间和紧邻数值框。
  色温/色调的有色轨道表达参数含义,不因材质统一而移除。
- 字体、行高、列宽、间距和命中区仍取现有角色 token。输入、拖动数值、
  键盘提交、双击复位与撤销行为保持一致,不按参考截图缩放字号。

### 2.2.3 底部材质浏览器与照片导航（2026-10-01，用户纠正后的规则）

照片导航与材质浏览器共用上方工具行、下方内容区的结构。照片导航在工具行显示
文件名/多选数量、拍摄光圈/快门/ISO 和复制粘贴操作,缩略图本身不增加文字说明。
材质浏览器采用上方选择控件、下方紧凑卡片的结构,
**整条共用一层 `EditorChromeSurface` 玻璃外壳**;内部工具行不再嵌套玻璃。
外壳和顶栏/参数面板沿用同一 regular 玻璃、衬底与 Ink 层级。

- 材质浏览器总高度为 160pt:上下 `space8` 内边距、28pt 工具行、`space8` 行间距、
  108pt 卡片内容。卡片宽 128pt、内边距 `space8`,封面采用 16:9 比例,
  高度由可用宽度计算,不使用独立的固定图片高度。
  照片导航总高同为 160pt,缩略图高 108pt,扣除共享工具行和内边距。
  保留原缩略图比例、选择框、多选与右键交互,整条使用同一玻璃外壳。
  二者共用 `modernBottomStripHeight`,画布遮挡计算使用同一来源。
- 两条底部工具行必须复用 `BottomStripToolbar` / `BottomStripToolbarGroup` /
  `bottomStripToolbarControl` / `BottomStripToolbarMenu`,不在各面板内另设字体或节奏。
  控件字体统一 `Theme.Font.bottomStripToolbar`（全局 label 角色,随界面缩放）,文件名和
  光圈/快门/ISO 使用相同字号,层级以墨色表达。行高 28pt、组间距 12pt、组内距 2pt、
  图文间距 4pt、文本按钮水平内边距 8pt、图标盒 14pt、纯图标命中区 28pt。
  菜单采用相同内边距、字体、选中墨色与控件圆角,显式共享尾部展开箭头;
  必须使用 `.menuStyle(.button)` 保留自定义标签,不能使用会重建标签的
  `.borderlessButton`（可能丢弃自定义星形、改用原生字号并把箭头移到前面）。
  窄布局只合并分类控件,不另设更小字号或不同间距。
- 星级与旗标筛选是底部工具行的“图标＋当前值＋尾部箭头”菜单控件,
  复用 `BottomStripToolbarMenu`,不另用原生默认下拉外观。
  星级图标使用与胶片“收藏”相同的实心 `RoundedFavoriteStar`;旗标使用 `flag`。

### 2.3 控件的状态

药丸 / 字段 / 按钮统一三层:填充、内描边、内容。状态做法固定:

| 状态 | 做法 |
|---|---|
| default | 平整填充 + 统一细边界 |
| hover | 共享 hover 填充,不位移或放大 |
| pressed | 共享 pressed 填充与边界,不模拟凹陷 |
| focus | 外圈 2px accent + 1px 间隙;**不改变填充** |
| disabled | 整体 38% 不透明度,但**保留内描边**(不能塌成半个控件);必须能说出原因 |
| selected | 见 §2.4 |

### 2.4 列表与选中

- 列表坐在 **well** 里,不是坐在 card 上。
- 选中 = 白色胶囊 + 1px 暗描边 + 极淡落影 + `onSelection` 文字;胶囊比行窄 2pt,不顶到边。
- hover = 淡填充(白 4–6%);**不加描边、不位移、不缩放**。

### 2.5 滑杆

- 轨道高约 3pt、全圆角;未过部分用暗版 rule,**已过部分用亮版 rule** —— 不用 accent,
  accent 只留给真正的"看这里"。
- 滑块直径约 9pt:1px 亮描边 + 1px 落影。hover 时**滑块不变大**,轨道提亮。
- 数值药丸固定宽度、等宽数字、右对齐。
- 拖动中:已过轨道与滑块同时提亮一档,数值药丸反白。

### 2.6 分隔与文字

- hairline:1px、**白 8%**。纯色线看起来像画上去的。
- 分区之间用 hairline;**行与行之间不用线**,用间距。
- 文字三级 `text / secondaryText / dim`;中文走系统中文回退,保持粗体语义。
- 数值一律 `monospacedDigit` + 右对齐;单位属于标签,不属于数值。

### 2.7 字体阶梯

只有四档,不新增:

| 档 | 用途 |
|---|---|
| 分区标题 | 区名 |
| 正文 | 胶片区的标签、列表分组标题 |
| 小号 | 相机区的标签、所有控件值 |
| 等宽数字 | 一切会变化的数值(缩放、EV、百分比) |

中文与英文配置名混排时**不要为了塞进去而降字号**;调整标签列宽。

**现代模式只用编辑器这一套**(2026-09-26 校准)。在此之前现代模式同时跑着三套字号:
分区标题走**导出页那份被冻结的刻度**(`Font.Export.sectionTitle` 12.5),底部胶片选择条
自己写了 10 / 11,蒙版区又写了 9 / 10 / 11。同一条栏里,分区标题比它的同级标题大,
比 `SectionMetrics.right` 声明的还大 —— 读者看到的就是"字号层级乱"。

现代模式的规则因此是两条,都由 `ModernCalibrationTests` 从源码上守着:

1. **视图里不许写 `.font(.system(size:))`**。`Theme.Font` 有角色就用角色,图标用
   `Theme.Metric` 的字号 token;只有"显示级"的字(空态的 34、启动页的字标)允许写字面值,
   门槛是 **17 pt** —— 17 以下是正文字号,属于角色,不属于视图。
2. **Modern 的分区标题是 `Font.modernSectionTitle`**(= `rightSectionTitle` 10.5
   semibold),不是导出页的 12.5。`Font.Export` 那一份按 TOKENS-v3 §9 冻结,
   只给导出页用,编辑器不许引用。

### 2.7.1 现代模式间距:栅格

**基准单位 `gridUnit = 4`。现代模式每一个"间距"和"高度"都是它的整数倍,而且必须是
`Theme.Metric` 里有名字的那几个。** 视图里的字面值就是逃出栅格的数。

| 名字 | 值 | 单位数 | 用在哪 |
|---|---:|---:|---|
| `space2` | 2 | ½ | **一个控件内部**(药丸文字到折角)—— 半格,4 会是个洞 |
| `space4` | 4 | 1 | 一行内部的两半(标签到它的框) |
| `space8` | 8 | 2 | 两行之间、一个簇里的两项之间、分区头到内容 |
| `space12` | 12 | 3 | 行块之间 |
| `space20` | 20 | 5 | 面板的内容 inset、分区内容到下一条 hairline |
| `modernPanelVerticalInset` | 16 | 4 | 面板上下 |
| `modernHeaderHeight` | 40 | 10 | 分区头 |
| `modernTopBarHeight` | 52 | 13 | 浮动顶栏 |

**两个刻意的例外,把理由写在这里而不是藏起来:**

- `gridRow = 22`(行高)。10.5 pt 的中文需要一个约 15 pt 的行框,上下各 3–4 pt 才读成
  "行"而不是"段";20 会切字的下缘,24 让 982 pt 的窗口装不下八行。22 是这个邻域里
  唯一两件事都成立的值。**所以栅格管间距是精确的,管行高是近似的。**
- `gridControl = 16`(滑杆、药丸、开关、字段的墨迹高度)。原来是 13.9 —— 一个从图纸
  量出来、和栅格无关的数。

定这个栅格之前的实测(2026-09-26):**一个检查器里有十一种行距**
(14.5 / 16 / 16.5 / 17.5 / 18 / 18.5 / 19.5 / 20 / 21 / 21.5 / 22),
**同一件事有两个分区-内容间距**(26 和 38)。这两个都不是某个视图写错 —— 每一个
单独看都合理 —— 几何断言也永远看不见它们。**一个单位才是让它们显形的东西。**

`ModernCalibrationTests.testTheModernGridIsFourPointsAndEveryGapIsOnIt` 逐条量这些
token 是不是 4 的倍数,并钉住那两个例外。

### 2.7.1b 已收口的高度

- **开关行 28 → 22。** 它用的是复选框的 28 pt 命中区当行高,所以同一个分区里开关行比
  相邻的滑杆行高 6 pt。现在两者同为 22,复选框的命中区改成**叠加的 `contentShape`**,
  布局不再为它付高度。
- **控件高 13.9 → 16。**
- **导出页:去掉页标题栏**(40 pt 的"导出",而窗口标题already 就是 Export),
  输出软打样的开关移进第一个分区的 •••;配方列表行距 18 → 22;列表到按钮、按钮行距、
  各种 9/14/16 全部进栅格。
- **`ExportPage` 里所有 `compact ? A : B` 删除** —— 窗口和栏读同一组值。

### 2.7.1c 还**没有**收口的(事实,不是允许)

**顶栏 52 pt**:它装文档名(12 pt 半粗)+ 状态/文件名(9 pt)两行,两行本身需要约 34 pt,
52 里有 18 pt 是空气。要不要压到 44 是个产品决定,不该由校准替你做 —— 压了之后
顶部三栏(左栏、中栏、右栏)的共享中线会跟着动,`trafficLightCentreY` 也要重算。

**导出页的表格行仍然比检查器的行多一步缩进**:导出页的标签列是 68.5(编辑器的 84 会把
四个命名 chips 裁掉),值从 88.5 起;检查器的控制从 104 起。两者的**标签轴相同**
(都在 20),不同的只是列的宽度 —— 那是宽度决定,不是第二套节奏。

### 2.7.1d 画布边缘:一道 gutter,两个家

**贴在画布边缘的东西,首项都落在 `modernSurfaceGutter`(12 pt)。** 这条是用户量出来的:
底部导航条首个缩略图在 **32 pt**,而它上面的直方图板在 **12 pt** —— 同一个画布的左边
出现两个左边缘。

原因和导出页那次是同一个形状:**同一道边距被应用了两次**。

- 容器(`EditorWindow` 的 overlay)已经给了 `modernSurfaceGutter`;
- 胶片条自己**又**加了一层 `stripInset = 20`(`modernContentInset`)。

所以规则是:`stripInset = 0`。画布上的 chrome 只有**一道** gutter —— 12 pt 定面板与
画布之间的缝、也定贴边内容与外框之间的缝:

```
贴边内容起始 = 12 pt          (直方图板、选择器板、导航条)
浮动面板左缘 = 窗口宽 − 344 − 12
导航条右缘   = 浮动面板左缘     (trailing = max(gutter, occlusion + gutter))
```

改完复量(1400×1200,2×):

```
选择器态  底部板左右缘 12.0 .. (面板左缘)
导航条态  底部板左缘   12.0  == 直方图板左缘
```

### 2.7.1h 行高的唯一来源

**`Theme.Metric.gridRow` 和 `Theme.Metric.gridControl` 是行与控件的唯一高度**,所有视图
都读它们。这一轮之前有四个地方还读着图纸时代的 `rowHeight` / `controlHeight`
(`FormatPicker` 两处、`UnitField` 的行、`CropSection` 的旋转行、`MasksSection` 的取色行),
所以同一栏里会混着 22 和 22、16 和 13.9 两种高度。

**这就是"顶部间距始终没改对"的机械原因**:分区头到第一项的**视觉**间距,取决于第一项的
墨迹有多高、以及它在行框里怎么放。第一项是**药丸**时墨迹 16 pt、两端各留 3 pt;第一项是
**纯文字行**时(如 `基准尺寸`)那一行根本没有行高框,于是它比邻居矮 —— 前者看起来多
12 pt。修掉那四处之后,同一栏的行距复量为 **17.0 / 17.0 / 16.5 pt**(改前是
18 / 19.5 / 24 / 17)。

**仍未收口的一条**:`UnitField` 的行现在有 `gridRow` 框,但它的**第一个**控件是纯文字,
和药丸行的墨迹高度仍差一行框的内边距。要彻底一致只有两条路,都是设计决定:

- **A** 所有分区首项统一从行框顶起(药丸不再垂直居中);
- **B** 按首项控件高度补偿"头→内容"的间距(每种首项一个值)。

### 2.7.1i 方案 A(2026-09-26,用户选择:"A 全部统一")

**每一行的框是 `gridRow`(22),框里的内容从框顶开始。** 不是垂直居中。

这一条同时收掉了三个症状:

1. **"顶部间距始终没改对"。** 分区头到第一项的视觉间距,原先取决于第一项墨迹多高、
   以及它在行框里怎么放:药丸 16 pt 墨迹居中 → 上下各留 3 pt;纯文字行没有行高框 → 比它矮。
   用户在"胶片"面板看到的那一行差就是这么来的。现在**六个 stage 的分区头到首项一律
   60.5–61.0 pt**,上一版是 38 / 43 / 40.5 / 50.5 四种。
2. **同栏行距。** 复量 17.0 / 17.0 / 16.5 pt(改前 18 / 19.5 / 24 / 17)。
3. **`modernPanelChrome` 环境值删除。** 它恒为真,所以它的每个分支都塌成现代那一支 ——
   而这正是"同一道边距被读两次"的结构性来源(`RailRows` 的 0/16、`PillMenu` 的
   `fill`、`SettingsRows` 的 0/16、`SectionHeader` 的两种头)。整套键、`SectionMetrics`
   类型和 `metrics:` 参数一并删除。

代价(明确接受):药丸与滑杆的墨迹在行框里**偏上 3 pt**,而不是居中。
换来的是"行"成为一个有统一顶边的单位,任何控件放进任何分区都不会改变
"分区头到第一项"的距离。

### 2.7.1j 控件列:一行一个控件,一列一个尺寸(2026-09-26)

用户:"我有强迫症,我需要这个 app 像专业软件一样有全局的视觉一致性。"

导出页「格式与尺寸」里同一栏的控件量出来是 **233 / 233 / 156 / 229 / 229 pt**。根因有三层,
每一层都是"同一件事有两种写法":

| 层 | 两种写法 | 后果 |
|---|---|---|
| 药丸实现 | `PillField`(导出页自己的:高 13.9、文字内边距 9、折角 8×5) vs `PillMenu`(全应用共享的:高 16、内边距 10) | **5 pt** 左缘差、2 pt 高度差、4 pt 宽度差 |
| 行的写法 | `row(_:)`(`HStack(spacing: 0)`)vs 手写 `HStack(spacing: 6)`,而深度药丸还用了 `.fixedSize()` | **6 pt** 左缘差、6 pt 宽度差 |
| 标签归属 | 行画标签(`row`)vs 药丸画标签(`labelWidth: labelColumn`) | 又一个 5 pt |

**规则(现在只有一条):** 一个表里**每行恰好一个控件**,标签由**行**画,控件撑满标签列之后
的整列。次要信息不新开控件,而是并入主控件的菜单条目文案 —— 所以"位深度"药丸被删除:
`ExportFormat` 本身就是"容器 + 位深"这一对,`withDepth` 是切换格式,那颗药丸是同一件事的
第二种说法。

改完复量(导出页设置栏,pt):

```
所有药丸行:  左 74.0   宽 233.0   右 306.5   高 15.0
剩下的不同值只有三类,它们是别的东西:
  滑杆圆钮 22×15.5    滑杆轨道 35×3.5    文字按钮 28×21
```

`PillFieldGeometry` 现在直接引用 `PillGeometry` 的值,两个形状不可能再各自漂移。
`ModernCalibrationTests` 的间距扫描继续守着字面值这一层。

### 2.12 控件分类学(2026-09-26,用户要求:"系统的、整体的、完整的定义这个软件的 UI")

**每一种控件只有一种形状、一种字号、一种高度。** 这不是风格偏好:同一个表里出现两种,
用户的眼睛会立刻把它读成错误("大大小小")。

#### 形状只有两种,由**动作**决定

| 形状 | 含义 | 用在哪 | 圆角 |
|---|---|---|---|
| **胶囊** | 执行操作 | 操作按钮、动作 chips | `Capsule`(无数字) |
| **圆角矩形** | 选择或输入参数 | `PillMenu`、`PillField`、单位选择、数值字段 | `modernControlRadius`(4.25) |

复选框与色块用矩形的圆角 —— 它们是方形控件,不是胶囊。

#### 五类控件,一种几何

| 类别 | 高度 | 字号 | 内边距 | 交互 |
|---|---:|---|---|---|
| **药丸**(选) | `gridControl` 16 | `Font.value`(值)/ `Font.label`(标签) | 文字 10、折角 9 | 点开列表,当前项带勾 |
| **字段**(输入) | `gridControl` 16 | `Font.value`,等宽数字 | 居中 | 回车提交,Esc 取消 |
| **滑杆** | `gridRow` 22 | 标签 `Font.label`,值 `Font.value` | — | 拖轨道/拖标签,双击复位 |
| **开关** | `gridRow` 22 | 标签 `Font.label` | — | 整行可点;命中区 28 叠加 |
| **按钮** | `gridControl` 16 | `Font.label` | 10 | 主按钮 accent 填充 + 暗字,一屏一个 |

#### 行的布局只有一条

```
[标签列 labelColumn] [控件槽 = 剩下的全部]
```

**"标签列"和"控件槽"是两个区域,间隙规则不同。** 标签与控件槽之间是 **0**;控件槽
**内部**如果有两个控件,它们之间是栅格的一道间隙(`space8`),而且槽本身撑满
(`maxWidth: .infinity`),否则第一个控件不会展开,间隙会变成两倍。

这一条是被一次真实错误写下来的:为了对齐标签把整条 `HStack` 改成 `spacing: 0`,
`0` 同时抹掉了标签→控件和控件→数值这两个不同的间隙,于是「尺寸」的药丸和它的数值框
**黏在了一起**。一个数字做两件事,而只有一件是对的。

```
标签  [ slot: 控件 ──8── 次要控件 ]     ← 槽内是栅格间隙,槽撑满
 └0┘
```

- **一行一个控件**时,控件撑满控件列 —— 所有行的左缘、右缘、高度完全相同。
- **一行两个控件**时(如「尺寸」+ 长边数值),主控件撑满**减去次要槽位**的部分,**次要槽位
  固定宽**(`fieldWidth`),中间是栅格的一道间隙。行的**外缘仍然与其它行完全相同**:
  读到的是一条子栅格,不是一个特例。
- **一行不超过两个控件。** 第三个信息并入最近控件的菜单条目文案(位深度就是这样并进
  格式条目的)。

#### 为什么这条规则重要(它换掉了什么)

| 曾经 | 现在 |
|---|---|
| `PillField` 高 13.9 / 内边距 9,`PillMenu` 高 16 / 内边距 10 | 两者引用同一组 `PillGeometry` |
| 数值框有时胶囊、有时矩形 | 由"选 vs 输入"决定,只有一种 |
| 长边数值框高 22、写死宽 62、胶囊 | 高 16、`fieldWidth`、矩形 |
| 同一表里有 `row()` 与手写 `HStack(spacing: 6)` | 只有 `row()` |
| 同一表里标签有时行画、有时药丸画 | 只有行画 |

#### 层级由**三级墨色 + 两档字号**表达,不由更多字号

```
标题   Font.modernSectionTitle  10.5 semibold   Ink.primary
标签   Font.label               10.5 regular    Ink.secondary
值     Font.value                9  medium mono  Ink.primary
说明   Font.caption              9  light        Ink.tertiary
```

**字号只有三档是产品决定**:层级靠墨色与位置,不靠字号。新增第四档字号之前先问
"能不能用墨色说清楚"。`ModernCalibrationTests` 守着这条(任何非显示级(≥17 pt)的
内联字号都失败)。

### 2.13 间距:块、行、墨迹带(2026-09-26)

用户问:"控件之间的间距是不是也应该有一致性规范?"

**行距(pitch)统一是不够的。** 实测胶片面板:行的 pitch 已经是 30 pt(22 行 + 8 间隙),
但**看得见的间隙**是 16.5 / 19.5 / 23.5 / 17.0 / 17.0 / 16.5 —— 差 7 pt。原因不是间距,
是**墨迹高度不同**:药丸的行墨迹 14 pt、滑杆 13.5、纯文字行 11、开关 11。间隙 =
pitch − 墨迹,所以墨迹矮的行看起来更空。

**规则:每个控件的墨迹都落在同一条 `gridControl`(16)高的"墨迹带"里,墨迹带顶对齐于
`gridRow`(22)高的行框。**

```
┌─ 行框 gridRow 22 ────────────────┐
│ ┌─ 墨迹带 gridControl 16 ──────┐ │
│ │  药丸的填充 / 滑杆的轨道与钮  │ │
│ │  / 数值文字 / 复选框         │ │
│ └──────────────────────────────┘ │
│ 6 pt 的余量(不属于任何东西)      │
└──────────────────────────────────┘
```

于是**行与行之间可见的间隙 = pitch − 16 = 6 pt,恒定**,不论那一行放的是什么控件。
这是"墨迹带"存在的唯一理由;只做顶对齐(方案 A)会把药丸和文字行差出 3 pt。

**块:一行附属的第二条线属于上面那一行,不是新的一行。**
滑杆的「拍摄时设置」、尺寸行的 `6336 × 9504 px` 都是这样 —— 它们和所属的行在同一个
`VStack(spacing: 0)` 里,块高 = 行框 + `subRowHeight`,块与块之间仍然是那一道 6 pt。
把附属线当成兄弟行(间距加在它两侧)会让它下面多出一整道间隙,读起来像换了个分区。

### 2.14 交互一致性(2026-09-26)

用户问:"所有的交互逻辑是不是也应该有一致性?"

**同一个动作在任何地方都是同一套手势与反馈。** 每种控件只有一种交互:

| 控件 | 打开/编辑 | 确认 | 取消 | 复位 | 精调 |
|---|---|---|---|---|---|
| **药丸** | 单击任意处展开 | 选中即生效并关闭 | Esc 关闭 | — | 上下键移动,回车确认 |
| **字段** | 单击进入编辑,文字全选 | 回车提交 | Esc 还原 | — | — |
| **滑杆** | 拖轨道**任意处**(不必抓钮) | 松手提交(一次撤销) | Esc 还原 | **双击**轨道/标签/数值回到零点 | ⌥ ×0.25 灵敏度,⇧ 吸附 |
| **开关** | **整行**可点,不只方块 | 即生效 | — | — | — |
| **按钮** | 单击 | 即生效 | — | — | — |

**相对位置也固定**:

- 标签在左、控件在右,标签独占 `labelColumn`,控件撑满剩余 —— 不因控件大小而变。
- 附属说明在该行**下方**,与滑杆标签同一起始 x(`labelColumn`),`Font.caption` + `Ink.tertiary`。
- 单位永远在数值**右边**,且是共享圆角矩形的选择控件。
- 复位/更多动作在分区头右侧的 •••,不在行里。
- 主按钮在分区/页面**底部**,一屏一个。

**状态与反馈(所有控件共用一套)**:

| 状态 | 视觉 | 不能少的东西 |
|---|---|---|
| hover | 只改填充/描边,**不位移、不缩放、不改变文字** | — |
| pressed | 填充压暗 + 内描边翻转 | — |
| focus | 一致的外圈焦点环,**不改填充** | — |
| disabled | 整行 38% 不透明(标签与控件一起) | **必须能说出原因**(tooltip) |
| selected | 白胶囊 + 暗字(列表);accent 字形(顶栏) | — |

**数值变化不做动画**(滑杆不该有延迟感);折叠/页面切换 180 ms `.easeOut`;hover 约 100 ms。

### 2.15 顶栏的语法(2026-09-26)

> **按功能排,不按现有代码排。** 用户的原话:"你不能按照现有的逻辑去排版,你需要从功能
> 角度出发,全局的看待这些问题。"

顶栏只有四个问题要回答,按**使用频率 × 位置稳定性**从左到右:

```
[窗口按钮]  工具  │  目的地  │  视图  │  动作
            选择  │  输入/拍摄 · 胶片 · 显影 · 彩色放大 · 扫描/输出 · 裁剪 · **导出**  │  对比 · 25% − +  │  [冲印]
            裁剪
```

| 组 | 回答的问题 | 频率 | 选中怎么表示 |
|---|---|---|---|
| **工具** | 点画布会**做什么** | 最高 | accent **字形** |
| **目的地** | 右栏**显示哪一段** | 高 | accent **字形**;六个阶段与导出互斥 |
| **视图** | 画布**怎么显示** | 高(看图时) | accent **字形**(对比);读数是墨迹,不表状态 |
| **动作** | **做**一件事 | 低(每帧一次) | accent **填充**,全栏唯一 |

**三个由功能推出、而非由代码推出的结论(2026-09-26 修正):**

1. **导出不是动作,是目的地。** 它的功能是"把右栏切到导出页",和阶段按钮**完全同一件事**:

   > 右栏现在显示哪一段?输入/拍摄、胶片、显影、彩色放大、扫描/输出、裁剪、**导出** —— 一个
   > 问题,七个答案。

   所以它进**目的地**组,在六个阶段之后,并且与它们**互斥选中**(`showExport` 亮时六个阶段
   全灭)。原先它在最右边和动作同组 —— 一个目的地读成了命令,而且这个软件**用得最少的按钮
   占了视线最后到达的位置**。

2. **缩放读数是读数,不是胶囊。** 参数选择使用共享圆角矩形,胶囊留给动作(§2.12);而顶栏
   其它控件全是裸字形。一个带底板的控件混在一排字形里,等于宣称自己是另一类东西 —— 而用户
   在这里**主要是读**当前倍率(菜单是次要路径:滚轮、⌘±、Fit 都能改)。所以它是**墨迹 +
   hover 淡底**(和每个字形一样),**顶栏上唯一的底板是主按钮的 accent 填充**。

3. **位置不是问题,形式才是。** 缩放和对比同属"画布怎么显示",放右侧是对的;错的是它比旁边
   的字形"重"。

**主按钮占常驻槽**(`primaryActionSlot`):「冲印」只在一帧刚显影时出现,写成 `if` 会让它右边
的每个控件随开图来回移动 —— 顶栏在指针下动。槽宽按最长文案定,**只有墨迹来去,布局不变**。
槽是顶栏的末端,后面没有分隔线。

**四组,三个分隔线,一组一条。** 之前三处分隔线落在四个位置,工具与阶段之间没有线,于是两个
模式和六个阶段看起来像同一类的八个。

#### 不放在顶栏的东西

- **渲染参数**(一切影响照片的数值)—— 右栏。
- **一次性动作**(除了那一个主按钮)—— 菜单或分区里。
- **第五个全屏入口** —— 绿色窗口按钮、⌃⌘F、View 菜单和手势已各有一个。
- **文档名与状态** —— 它们是**叠加层**:居中、`allowsHitTesting(false)`、窄窗口
  (<1100 pt)隐藏而不是挤压控件。

### 2.15b 旧文:四组的分法(已被上文取代)

用户:"看看这个顶栏吧,充斥着几种完全不一样的东西和逻辑。"

顶栏是**唯一一条横跨整个窗口的 chrome**,所以它的分组必须能一句话说清。现在是一句话:

```
[窗口按钮]  工具  │  阶段  │  视图  │  动作
            选择  输入/拍摄  对比     [冲印] 导出
            裁剪  胶片      25% − +
                  显影
                  彩色放大
                  扫描/输出
                  裁剪
```

**四组,三个分隔线,一组一条。** 分组由**动作的语法**决定,不由控件的外观决定:

| 组 | 语法 | 选中怎么表示 |
|---|---|---|
| **工具** | 改变"点画布会做什么" | accent **字形** |
| **阶段** | 改变"右栏显示哪一段" | accent **字形** |
| **视图** | 改变"画布怎么显示" | accent **字形**(对比);读数药丸不表状态 |
| **动作** | 做一件事 | 主按钮 accent **填充**,一屏一个 |

**一条线只画在两组之间。** 之前是三处分隔线落在四个位置:工具与阶段之间没有线,于是两个
模式和六个阶段看起来像同一类的八个。

#### 三个具体错误,及其规则

1. **四种"选中"语言。** 阶段是 accent 字形、对比是 accent 字形、导出是 accent 字形 —— 这三
   个已经统一;**药丸不应表达状态**。`25 %` 是读数,它永远不该变色。主按钮是 accent 填充
   (它不是"选中",是"做这件事")。
2. **两个行高。** 药丸是图纸的 20.69,图标在 28 的命中区里,于是读数比旁边的东西离中心线更远。
   规则:**顶栏只有一个行盒 —— `gridControl`(16)**;图标在自己的 28 命中区里居中,药丸
   16 高,分隔线 16 高,全部落在同一条中心线上(`zoomPill.height` 因此改了)。
3. **会消失的主按钮把右边推走。** 「冲印」只在有负片时出现,写成 `if` 时它右边的每一个控件
   都会随开图来回移动 —— 顶栏在指针下动。规则:**主按钮占一个常驻的槽**
   (`primaryActionSlot`),槽宽按最长文案定,只有**墨迹**随状态来去,布局不变。
   **槽不单独成组**:它和导出按钮同属"动作",中间不画线(否则没有负片时会出现两条线夹着
   一块空白)。

#### 不放在顶栏的东西

- **渲染参数**(一切影响照片的数值)—— 它们在右栏。
- **一次性动作**(除了那一个主按钮)—— 它们在菜单或分区里。
- **第五个全屏入口** —— 绿色窗口按钮、⌃⌘F、View 菜单和手势已经各有一个。
- **文档名与状态** —— 它们是**叠加层**,不是控件:居中、`allowsHitTesting(false)`,
  在窄窗口(<1100 pt)隐藏而不是挤压控件。

### 2.16 七个目的地,一种栏体(2026-09-26)

用户:"你的 stage 面板形式还是没能做到统一,现在导出是一个样式,其他六个是一个样式…
他们七个 stage 是完全同一层级吧?"然后是:"我觉得导出这个形式更好,因为后续每个 stage
里面可能会加别的功能可能会更长,但是下滑的时候显然要让标题栏在顶部。"

**七个目的地是同一层级,所以栏体必须相同,而且标题必须钉住。**

```
右栏 = ┌──────────────────────────┐
       │ 阶段头(钉住)  名称 · ••• │  ← 不随内容滚动
       ├──────────────────────────┤
       │ ScrollView               │
       │   该阶段的内容            │
       └──────────────────────────┘
```

**为什么钉住**(采纳用户的判断,它比"不要标题栏"更好):每个 stage 以后都会变长,
而**一个名字滚走的 stage 是你失去位置感的 stage**。导出的内容先长起来,所以它先有了
标题栏;现在这是**七个的规则**。

**名称只出现一次。** 参数阶段的第一个分区标题**就是**该阶段的名字,所以:

- 阶段头画名字(`StageHeader`,钉住);
- 该分区在栏内**不再画名字**(`PanelSection(stageOwnsTitle: true)`),它那一行只剩 **•••**
  与其右对齐的动作 —— 菜单一个字都不用搬,名字也不重复。

导出页不同:它的 stage 是**一页五个分区**(配方 / 位置 / 命名 / 格式与尺寸 / 摘要),
所以它的分区保留自己的名字,阶段头只负责页面名与"输出软打样"。

复量(1400×900,2×,pt):

### 2.16a 每个 stage 的 ••• 都必须有重置(2026-09-26)

用户:"为了保证一致性应该在导出整个面板右上角的菜单里放一个重置,其他所有没有菜单的
stage 也应该如此。"

**一个 stage 是一组设置,"把这组放回去"是每一组都有的那一个动作。** 一个菜单为空的
stage 是用户无法从中撤销的 stage。所以:

| stage | ••• 里的重置 |
|---|---|
| 输入 / 拍摄 | 重置曝光补偿 |
| 胶片 | 重置胶片 |
| 显影 | 重置显影 (**新加**,原先没有菜单) |
| 彩色放大 | 重置相纸配置 |
| 扫描 / 输出 | 重置本节 (**新加**,原先没有菜单) |
| 裁剪 | 重置裁剪 |
| 导出 | **重置此配方** (**新加**) —— 保留配方的 id 与名字,它们是它的身份 |

**"这一组的重置"与"这个控件的重置"不同**:控件级复位是双击(§2.14),分组级复位在 •••。
两者都在,而且是两个不同的动作,不合并。

### 2.16b 块内不要"首块间距"(2026-09-26)

用户:"我怀疑胶片 stage 和彩色放大 stage 的标题栏和第一项内容的中间有某种多余的间距…
视觉上看起来永远比其他的多一点。"

**他是对的,代码里真有。** `FilmSection` 的第一个 `RailRows` 与
`PrintProfileSection` 唯一的 `RailRows` 都带着 `.padding(.top, modernBlockGap)`
(12 pt),而 `CameraSection` 没有 —— 于是那两个 stage 的标题下面永远多一截。

**规则:`blockGap` 只画在两个块之间。** 一个上面什么都没有的块带一个块间距,就是标题
下面的空气。第一个块**没有** `.padding(.top)`。

### 2.16c 开关放进它作用的块(2026-09-26)

用户:"导出里的输出软打样,我觉得应该放在某个内容块里面做成一个开关不是吗?"

**对。** 它先是标题栏里一个带文字的按钮,后来是配方菜单里的一项 —— 两个都不是它:
它不是页面的身份,也不是一条命令,而是**判断结果时打开的一个状态**,那是开关的用途
(§2.14)。位置:**配方块内**,在配方列表下面 —— 被软打样的是配方。

### 2.16d 开关只有一种形状(2026-09-26)

用户:"现在开关这种控件似乎也没有统一规范,我认为文字在最左侧方框在最右侧是对的,
所以拍摄 stage 里面的拍摄时设置那几个开关显然有问题了,而且他们都是说明文字,按理说
不应该给他一个开关。"

**参数启用行的规则:**

```
┌─ 行 ────────────────────────────────────────┐
│ 标签(最左,内容边)          [可选第二行]   ☐ │  ← 方框贴最右
└─ 整行可点 ──────────────────────────────────┘
```

- 标签在行框的**最左**(内容边)。方框的**可见右边缘**必须与同分区数值框、菜单的
  可见右边缘共用同一条内容基线;不以点击区域外框或容器边缘代替方框边缘。
- 方框位于 `gridControl` 布局容器中央。行尾补偿只取
  `checkboxTrailingInset = -(gridControl - checkbox) / 2`,不使用 `controlHitTarget`
  计算位置。原先使用命中区计算负边距会让方框多伸到内容边界外。
- 参数启用行、拍摄时设置行、导出选项行共用这一对齐 token,各处不另写负边距。
  复制设置列表里的前置勾选框仍按文字前方的列表规则排版,不套用行尾补偿。
- **整行可点**,不是只有方框可点;
- 方框的**命中区 28** 由 `contentShape` 扩展布局容器提供。
  扩展量为 `checkboxHitOutset = (controlHitTarget - gridControl) / 2`;
  点击区域独立于可见方框,不增加行高,也不改变横向对齐。
- 纵向与同一行的输入框、菜单共用 `gridControl` 墨迹带中心;不能通过扩大点击框
  或局部上下偏移来修复看起来不齐的问题。
- 可选第二行(说明)在标签**下面**,与标签同左缘;
- 关掉时它管辖的从属控件一起置灰并保留原位。

**"拍摄时设置"那几个为什么看起来不对(以及它其实是什么)。**

它是一条**开关**:"这个值是相机记录的" —— 打开 = 用拍摄值。原来的形状是
**一句小字 + 紧跟其后的方框**,于是文字读成"说明",方框读成"粘在句子后面的东西";
用户问"说明文字为什么有开关",很自然。**错的是形状不是存在**:现在它与所有开关同形
(文字最左、方框最右、整行可点)。

### 2.16e 一个动作只能有一个家(2026-09-26)

用户截图里导出标题栏右侧仍是「输出软打样」—— 因为那次改动只落在**侧栏那一份**,
`compactPanel` 里的旧按钮没删。这是本轮最贵的教训之一:

> **同一段界面在两个家(侧栏 / 独立窗)里各写一遍时,改一处不等于改完。**

规则:导出**只有一个** "输出软打样",它是**配方块里的开关**(§2.16c);
stage 头是名字 + •••,没有例外。改这类"两处实现"时,两处一起改,并在同一次提交里核对。

### 2.16f 层级:stage > 块,••• 永远属于块(2026-09-26)

用户:"为什么导出的配方实际上是'配方'的菜单,而'配方'没有真正的属于自己的内容块标题,
导出这个面板的层级是不是要重新规划?"

**对,而且是我上一轮的机制造成的。** `导出配方` 这个块**原本有自己的标题和 •••**;当我把
它的菜单"上报"给 stage 头之后,`PanelSection` 的规则是"有 stageMenu 就不画标题行" ——
于是**标题和 ••• 一起消失**,菜单跑到 stage 头上。结果:stage 标题写着"导出",它的 •••
装的却是**配方**的动作,而配方自己没有标题。

**层级规则(现在只有这一条):**

```
stage(钉住的头:名字)
  └─ 块(标题 + 自己的 •••)
       └─ 行
```

| stage 的形状 | stage 头 | 块 |
|---|---|---|
| **一个块**(输入/拍摄、胶片、显影、彩色放大、扫描/输出、裁剪) | 名字 + **该块的 •••**(块的标题就是 stage 的名字,再画一遍是重复) | 无自己的标题行,内容直接进 |
| **多个块**(导出:配方 / 位置 / 命名 / 格式与尺寸 / 摘要) | **只有名字** | 每块自己的标题 + 自己的 ••• |

导出栏因此读作:**导出** → **导出配方 •••** → **位置 •••** → **命名 •••** → **格式与尺寸** →
**摘要**。stage 的"重置"落在配方块的 •••(重置此配方)——因为导出的"那组设置"**就是配方**。

**自检(一句话)**:一个 `•••` 打开后,里面每一条动作是否都属于**它上面那一个标题**?
答"否"就是层级错了 —— 这次就是。

### 2.16g 导出页的信息架构(2026-09-26,重新判定)

用户:"导出这个大 stage 没有自己的菜单;导出里面每个内容块其实都属于导出配方的附属层吧?
那他们的子菜单就不再显得[必要]了,实际上现在我觉得大部分都不太有必要,从功能逻辑上来说。
导出整个面板的逻辑要重新判断。"

**这个页面的模型是"一列配方 + 所选配方的各项设置":**

```
导出(stage)
├─ 配方            选哪一个
│    ├─ 位置        写到哪
│    ├─ 命名        叫什么
│    ├─ 格式与尺寸   是什么
│    └─ 摘要        会得到什么(只读)
```

四个块**不是并列的分组,是同一份配方的四个侧面**。这决定了两件事:

**① stage 必须有它自己的 ••• —— 用来放"不属于任何块"的动作。**
今天只有一个:在访达中显示**配方文件**(store 自己的文档,没有任何块表示它)。
其余动作都关于**所选配方**,归配方块。

**② 一个块的 ••• 里的每一条,都必须是"块里画不出来的动作"。**

| 块 | 原来的菜单 | 判定 |
|---|---|---|
| 位置 | 选文件夹 / 用照片文件夹 / 清除子文件夹 / 在访达中显示 | **四条全是它自己行上已有的东西** —— 删掉整个菜单 |
| 命名 | 仅用原文件名 / 全选 / 重置顺序 | 前两条是"点四次"的批处理,第三条作用在一个页面上根本没画的 chip **顺序** —— 删掉 |
| 格式与尺寸 | (无) | — |
| 摘要 | 复制摘要 | **保留**:只读块的唯一动作就是把它拿走 |
| 配方 | 新建 / 重置此配方 / 复制 / 重命名 / 删除 | **保留**:全是列表与所选配方的动作 |

**自检(与 §2.16f 同一句)**:打开一个 •••,里面每一条是否都属于它上面那一个标题?
另外问一句:**这一条是不是已经在屏幕上作为一行存在?** 是,就删掉菜单项 —— 菜单不该重复自己的行。

**③ 输出软打样放哪。** 用户问"现在还觉得它应该在导出配方这个内容块下面吗?"—— **不应该。**
它不是配方的属性(配方里不保存它),而是"**给我看这份配方的结果**"。所以它在**摘要块**:
紧接在"会得到什么"的清单下面 —— 一句话读作"……以及,把它显示在画布上"。
它到过三个地方(标题栏按钮 → 菜单项 → 配方列表下的一行),这三个都不是它。

### 2.7.1k 旧文(保留作为对照)

原来的 5 值标尺(2/4/8/12/20)是这套栅格的来源,内容已并入上表。

`Theme.Metric.space2 / space4 / space8 / space12 / space20`,2/4/8 是翻倍链,12 和 20
是另两级。**现代模式的每一个 inset 和 gap 都是这五个值之一**;需要第六个值的视图,
其实需要的是这五个里的某一个。

| token | 用在哪 |
|---|---|
| `space2` | 一个控件内部(药丸的文字到折角) |
| `space4` | 一行内部的两半(标签到它的框) |
| `space8` | 两行之间、一个簇里的两项之间 |
| `space12` | 面板边缘到它的表面、行块之间 |
| `space20` | 浮动面板的内容 inset、一个分区的内容到下面那条 hairline |

校准前现代模式有**四套并存**的间距:浮动外壳的 12/20、图纸时代的 16/9、底部选择条自己的
8/7/4,以及散落的 2/3/4/5/6/7/8/10/14/18/20 字面值。用户的读法是"间距不统一"**和**
"整体偏松",这两句是一件事:没有标尺时,每个 gap 都是一个独立决定,而松的那些没人抓得住。

配套的四个决定:

- **`modernContentInset` 只被应用一次。** 面板自己 pad 一次,分区**不再**把自己的
  `bottom` 也 pad 成同一个值 —— 那会让最后一个分区下面出现 40 pt 的空白,而第一个分区上面
  只有 20(2026-09-23 间距审计)。分区只负责"内容到 hairline 之间"的空气。
- **面板的上下 inset 比左右小一档**(`modernPanelVerticalInset` 16 vs 20)。垂直 inset
  一屏出现两次,除了把内容从表面边上推开,没有任何作用;水平 inset 是全栏对齐用的,所以留 20。
- **行距 8、行高 22**(`modernRowSpacing` / `modernRowHeight`)。图纸时代的 9 是给
  254 pt 的栏用的,现代的面板按同一个节奏读起来散。勾选行仍是 `toggleRowHeight` 28:
  那是命中区要求的两个 14 pt,不是第二套行高。
- **标签列 84**(`modernLabelWidth` = `sliderLabelWidth`)。相机与胶片、左栏与右栏,
  一列一轴,不做第二列。

### 2.7.2 现代模式的圆角:只有三个

`modernControlRadius`(=`fieldRadius` 4.25,方形控件)、`modernCardRadius`(9,卡片大小的
格子、选择器卡片)、`modernContainerRadius`(16,一切浮在画布上的表面:两条栏、顶栏、
直方图板、底部条)。列表的选中胶囊用 `modernSelectionRadius`(=`stockSelectionRadius`),
那是它自己高度的一半,不是一个第四种圆角。

校准前一个窗口里同时活着 2、4、6、7、9、11.5、14、16 八种圆角,而 §2.10 明说
"一张图里出现两种圆角"是禁止的。

**嵌套表面规则**:圆角按语义层级使用,不能让卡片借用字段的控件圆角。
同一表面的内描边才由 `nestedRadius(外圆角, 内边距)` 推导,
即 `max(0, 外圆角 − 内边距)`。独立图片不是内描边,不能随留白增大而被压成直角。
材质卡片用 9pt,图片内缩 `space8`,图片裁切使用共享 modernControlRadius 4.25pt;
外壳仍用 16pt。
材质工具行与卡片列表共用外壳 `space8` 左边界,工具行不再二次缩进。
卡片文字距卡片边缘 `space8`,图片距边缘 `space8`;首个切换按钮内容也内缩
`space8`,与第一张卡片文字对齐。名称/元数据间距 `space2`,图片/文字间距 `space4`。
圆角轮廓统一使用 continuous。收藏按钮只显示星标,不添加底色或圆角底板;
保留 28pt 透明命中区,距卡片右上角 `space2`,字形为 14pt。
卡片与顶部收藏筛选共用 RoundedFavoriteStar,尖端和内凹转角使用圆润曲线。
未收藏为细线空心星,收藏为 accent 实心星;在白色占位图片上使用深色图标保证辨识度。

### 2.7.3 图标:现代模式每个层级一个字号、一个命中区

- 行内字形 `modernRowGlyph`(11),子层字形 `modernSublayerGlyph`(9)。
- 纯图标动作的命中区 `modernIconTarget`(=`railIconTarget` 26);顶栏用
  `controlHitTarget`(28),因为顶栏的行更高。
- 字形大小不许写成函数的默认参数(`size: CGFloat = 11` 又让调用点传 9,就是两套刻度)。

范围是**现代模式**(2026-09-26,用户要求"进行一次全局的 UI 规范校准 … 主要针对现代模式")。
以下是刻意留在这里的,理由各不同:

| 没动 | 为什么 |
|---|---|

| **导出页的几何** | 正文已经统一(见上),但 `Metric.Export` 里**只有更大窗口才装得下的几何**留着:卡片宽度、独立窗口的 well 缩进、144 pt 的配方列表。它没有第二套节奏。 |
| **设置 / 关于 / 启动页** | 与模式无关的独立窗口。设置页仍渲染**传统**的 30 pt 栏头(它没有设 `\.modernPanelChrome`),关于页仍有 20 / 13 pt 的标题字,启动页整套几何都是窗口自己的。它们是下一轮的对象,不是这一轮的漏项。 |

### 2.8 图标

- 一律 SF Symbols,统一 weight;只有两档尺寸(栏头 / 行内)。
- 与相邻文字**光学对齐**,不是按字号框对齐。
- 纯图标按钮命中区 26×26,必须有 `.help(...)`。
- 图标不表达状态;状态用颜色、文字或位置。

### 2.9 画布叠加层

画布上的东西是**画在照片上**的,不是浮在照片上的卡片:

- 它属于 L4,但**只允许落影,不允许底板颜色、圆角、内边距**。
- 可读性靠一层极淡的顶部渐变压暗(约 12% → 透明),不靠一块灰。
- 直方图固定在**右上角**,徽章在其下方,共用一条纵向间距规则。
- 叠加层可开可关,顶栏给开关,状态持久化,默认开。
- 叠加层不拦截拖动;除拾取类工具外,画布上的点击都属于画布。

### 2.10 什么会显得廉价(禁止)

| 禁止 | 改成 |
|---|---|
| 用纯色 1px 边框勾控件 | 上亮下暗的内描边 |
| 每层都加圆角和投影 | 投影只给 L4 |
| hover 时位移、放大、抖动 | 只改填充与描边 |
| accent 到处用 | accent 一次只在一处 |

**accent 的定义(2026-09-23,用户要求)**:`Theme.accent` = **Apple 橙 `#FF9F0A`**
(`NSColor.systemOrange` 的深色外观取值;浅色版是 `#FF9500`)。理由就是 accent 唯一的
工作是"被认出来",而人认得的橙是系统那个 —— 它替掉了 v3 图纸采样出来的 `#E1A95F`
(一个土黄)和更早的 `#ee8a2b`。写成字面值而不是 `Color(nsColor: .systemOrange)`,
是为了不让界面在系统外观/辅助功能设置/OS 更新下移动。

**accent 保持纯色**。主动作与选中复选框用统一橙色;灰色控件也采用平整填充,
不再使用 `pillSurface` 顶光渐变。细边界和 hover / pressed 反馈由共享样式提供。
- 不属于这一条的橙色有两处,都是**照片的东西而不是界面**:擦除动画里那盏暖色灯
  (`Shaders.metal` 里的 `float3(1.0, 0.87, 0.64)`)和底片本身的橙色罩(引擎的物理),
  以及白平衡轨道的 `#FFF100` 端点(那是**色标**,不是装饰)。
| 数值用比例字体(会左右跳) | 等宽数字 |
| `Color.gray` / `.black.opacity()` 这类即席色 | `Theme` token |
| 手工模糊 / 渐变模拟玻璃,或在原生玻璃后堆不透明底板 | 内容区用实底层次,浮动导航与工具层用原生 Liquid Glass,模态弹窗沿用系统呈现(§2.2.1) |
| 一张图里出现两种圆角 | 一种控件圆角 |
| 大图标、插图、吉祥物式空态 | 一句话 + 一个动作 |

### 2.11 动效

以 §6 为准。摘要:hover 约 100ms、按下即时、面板折叠约 180ms;**数值变化不动画**。

## 3. 组件规范

每个组件必须写清**结构 / 状态 / 交互**三件事。状态至少包含
default、hover、active、focus、disabled 五种;缺哪个要有理由。

### 3.1 滑杆(参数的主力)

- 结构:标签列 | 轨道 | 数值药丸。单位与方向写在标签的第二行,不写进数值。
- 交互:
  - 拖动轨道:改值,按 `snap` 吸附。
  - 拖动**标签**:同样改值(scrub),这是老手的路径。
  - 双击标签或数值:回到该参数的默认值(`zero` 或默认档)。
  - 单击数值:进入输入,回车提交,Esc 取消,非法输入回弹并提示。
  - 键盘:聚焦后方向键 ±1 步,⇧ 方向键 ±10 步。
- 状态:hover 时轨道提亮一档;active 时数值药丸反白;focus 时有一致的焦点环;
  disabled 时必须能通过 tooltip 说出原因。
- 拖动整段只算**一次撤销**。

### 3.2 下拉药丸

- 结构:标签 | 药丸(当前值 + 折角)。
- 交互:点击展开;菜单项当前项带勾;上下键选择,回车确认,Esc 关闭。
- 值多到超过 5 个时,考虑换成带搜索的菜单,而不是更长的列表。

### 3.3 开关行

- 整行可点,不是只有开关可点。
- 关掉一个开关时,**它管辖的从属控件一起置灰**,并保留在原位(不塌陷、不消失)。

### 3.4 分组列表(胶片 / 相纸)

- 正面/负面、静态摄影/电影是分组标题,不是可选项,不参与键盘选择。
- 选中用白胶囊 + 深色字;hover 用淡底;键盘上下移动选择,回车确认。
- 列表本身可滚动,滚动条不常显;分组标题吸顶。

### 3.5 数值字段

- 可输入。非法值不静默接受:回弹 + 说明。
- 单位属于标签,不属于输入框;输入框里只有数字。

### 3.6 按钮四级

| 级别 | 用途 | 出现位置 |
|---|---|---|
| 主按钮 | 一屏一个,推进流程(自动测光与配光) | 分区底部 |
| 次按钮 | 重置、次要动作 | 分区底部或标题栏 ••• |
| 图标按钮 | 视图类、工具类,有 tooltip | 顶栏、栏头 |
| 危险按钮 | 删除类 | 菜单内,或带确认 |

同一屏不出现两个主按钮。

### 3.7 分区头

**两种头,两种结构,不要互相套用:**

| 表面 | 结构 | 折叠 |
|---|---|---|
| **传统栏**(左/右栏) | 展开三角 \| 标题 \| (可选)••• | 整行可点,状态持久化 |
| **现代检查器 / 导出栏 / 独立导出窗** | 标题 \| ••• | **没有折叠**:一次一个阶段,换阶段用顶栏的 stage 按钮 |

现代头不画三角,`expanded` 在那里不生效 —— 不画就不该有。••• 里的动作必须与分区同域,
并写明作用范围。

### 3.8 空态

- 一句中文说清"这里为什么是空的",加一个动作(如胶片条:按 ⌘O)。
- 空态不用插图、不用大图标。

## 4. 交互模型

### 4.1 鼠标与修饰键

| 操作 | 结果 |
|---|---|
| 拖动滑杆标签 | 调值(scrub) |
| 双击标签 / 数值 | 复位到默认 |
| ⇧ + 拖动 / 方向键 | 精调(10× 更细 / ±10 步) |
| ⌥ + 拖动 | 减速,便于精确定位 |
| 右键 | 上下文菜单(画布、列表、参数行) |
| 滚轮 / 触控板 | 画布缩放(以指针为中心);列表滚动 |

**同一个操作在所有同类控件上行为一致。** 一个滑杆能双击复位,所有滑杆都要能。

### 4.2 画布

| 操作 | 结果 |
|---|---|
| 拖动 | 平移(空间键按住 = 临时平移工具) |
| 滚轮 / 双指 | 以指针为锚缩放 |
| 双击 | 在"适合窗口"与 100% 之间切换 |
| 对比模式 | 拖动分界线;Y 键切换 |
| 白平衡吸管 | 按下拾取、松开应用;Esc 取消;拾取时显示放大镜 |
| 裁剪 | 八向手柄 + 三分线;回车提交,Esc 取消 |

### 4.3 键盘

- Tab 能在参数栏里走完所有可交互控件;焦点环统一。
- 分区可用快捷键折叠/展开,但快捷键不写进译文。
- 所有菜单动作都有快捷键,并且**菜单栏与顶栏是同一动作的两个入口**,不是两套实现。

### 4.4 撤销

- 每一次参数改动入栈;⌘Z / ⇧⌘Z。
- 一次拖动、一次输入提交 = 一次撤销,不是每帧一次。
- 视图状态(缩放、面板折叠、叠加层开关)不进撤销栈。

### 4.5 工具提示

- 统一延迟出现,内容包含:它是什么、单位、范围、以及禁用原因(若禁用)。
- 提示文字也算用户可见文案,必须走本地化(§7)。

## 5. 状态与反馈

### 5.1 四种状态,每种都有出口

| 状态 | 表现 | 出口 |
|---|---|---|
| 空 | 一句话 + 一个动作 | 该动作 |
| 忙 | 进度指示 + 可取消 | 取消键 |
| 禁用 | 变灰 + 原因 tooltip | 说明如何解除 |
| 错误 | 一句人话 + 一个可执行动作 | 重试 / 打开位置 |

**不允许出现"看起来能用但没反应"的控件**,也不允许"变灰但不说为什么"。

### 5.2 渲染与加载

- 渲染中:画布角上给状态,不用全屏遮罩。
- 提高分辨率时保留上一张画面,不要闪成空白。
- 超过约 1 秒的阻塞必须能看到反馈。

### 5.3 错误

- 不把系统错误直接抛给用户;包装成"发生了什么 + 怎么办"。
- 不弹模态对话框处理可恢复错误。

---

## 6. 动效

- 只有三处动画,时长统一:面板折叠(~180ms ease-out)、悬停反馈(即时)、值变化(不闪)。
- **值变化不做动画**:数值等宽,原处刷新。
- 禁止弹跳、缩放、旋转类装饰动画。
- 尊重系统"减弱动态效果"设置。

**「打开即显影」的策略修正(2026-09-23,用户报"拖入照片看到的还是原图,点按钮才出片"):**

查到底后的三条事实:

1. **那个按钮是空的。** ctypes 探针比较"打开后"与"`solve(both)` 后":所有参数一个没变
   (中性滤色值/放大曝光在打开时就是解算值),**像素逐位相同**(0 / 110592 采样点变化)。
   测光在打开时已跑,中性滤光值在 `digest` 里由数据库写入。所以它唯一的效果是**触发重画**。
2. **开发是有门的,而且门不稳定。** `load` 末尾有 `guard wantsDevelop else { … "press Solve
   to develop it" }`。`select()` 开头把 `wantsDevelop = false`,但打开路径里
   `recomputeFilmFormat` 等**会写 params**,而 `params.didSet` 会 `requestPrint()` ——
   于是**单张拖入会显影,点胶片条切帧不会**。
3. **画布把解码当成品。** 解码图被 `setLive` 当画面,角标只写 "preview",读起来像
   "这是你的成品(预览分辨率)"。实测 60 MP 帧:第一张成品 4.4 s,全分辨率再 4.8 s。

修法:

- **每一帧被选中就请求显影**(`select` 里 `wantsDevelop = true`):每帧都有胶片和相纸,
  所以每帧都该有成品。切帧仍有打印缓存兜底(先秒显旧片,再刷新)。
- **解码不再上画布**(`select` / 原生解码 / display-cache / decode 四处去掉 `setLive(解码)`)。
  解码仍然保留给「原图」和全分辨率渲染对齐用。
- 成品落地前画布是**空的中性底 + 角标「显影中…」**;成品落地即显示(成品在时不再重复
  显示 "preview")。
- **删除 Solve 按钮及其整行**(它证不出任何效果);`solveNow` 保留为程序化重解算。

**注意**:钉住旧策略的测试(`OpenPathTests.testTheCanvasDrawsTheNativeDecodeBeforeADevelop`
等)属于本机 39 个 **skipped**(缺相机 fixtures),所以这次行为改动**由抓图验证,不是由测试
验证** —— 那几条断言需要连同 fixtures 一起复审。

**负片→正片的仪式(2026-09-23,用户提的设计,已实现):**

继承原作者的"导入是底片、冲印才出片",但把它从**门槛**变成**第一张的仪式**:

- **引擎**:新增 `spk_preview_scan(session, tier, out)` —— 在**参数探测副本**上把
  `io.scan_film` 打开,复用缓存的负片、只跑印相阶段,返回后 session 原样恢复。
  之所以要新入口而不是直接切 `scan_film`:那个字段是**用户可见参数**(相纸列表里的
  「不使用相纸配置」),切它会让界面跟着跳。ctypes 验证:参数不变、之后的 reprint 与
  首印逐位相同、耗时 2.7 ms(负片命中缓存)。

  *怎么动* —— 只有画布知道一帧什么时候在被画。**这一层从第一版起就没变过,
  变的全是"画什么"。**
- **当前效果（2026-10-01）**：移植 Andrea Volpato spektrafilm 的
  `polaroid_animation.py` 密度分层和时间曲线。移除横向光带；负片短暂
  转入纸白，中性密度、黄、品红、青在整张画面上错峰浮现，临时色偏消退。
  这些是成片重建的视觉层，不是真实乳剂子层或显影动力学模拟。

  不套用上游显示 RGB 的 gamma 2.2。使用固定密度归一化，不保存九张
  全图层或逐帧重跑引擎。末段平滑恢复原始值；进度 1 直接采样成片，

**印相区那两个胶囊(同一次排查的起点):**

原来是一对同形状的描边胶囊:「配光」+「原图」。查清后的三个问题:

1. **名字只说了一半**:「配光」只指滤光片组合,而 `solveNow()` 做的是
   `solve(target: "both")` —— **测光 + 为所选相纸解算中性滤光片(Y/M)并把偏移归零**。
   准确的字符串「自动测光与配光」本来就在 `Strings.swift` 里,只是用在了别处。
2. **同一动作两个入口**:区菜单里还有一条同名项,调同一个 `solveNow()`。
3. **把"动作"和"视图状态"配成一对**:「原图」是*看什么*,不是做什么,两个却画成
   一模一样的胶囊 —— 于是读成两个动作。

修法:印相区只留**一个主按钮**(accent 填充,§3.6),标签用完整的那句;菜单里的重复项删除;
「原图」搬到顶栏**视图簇**(和「对比」并列,两者都在回答"我在看什么"),激活时 accent 填充。
`solveNow()` 内的那句自述留在按钮的 tooltip 里。

**顶栏的间距机制(用户反馈"图标乱糟糟、间距都不对"):**

- 图纸的四个一次性间距(工具间 33、缩放药丸两侧 23、对比前 40、全屏前 46)换成**两级尺度**:
  簇内 `barItemGap`(4)、分隔线两侧 `barClusterGap`(10),簇之间用 1pt `ruleSoft`
  竖线分开。四个数做一件事正是"散"的来源。
- **全屏按钮删除**:绿钮、⌃⌘F、View 菜单、窗口手势都能做同一件事,而它是顶上唯一
  与照片无关的字形。`fullScreen` 状态与两个通知观察者一并删掉。

**左栏高度(用户问"是不是要对应增加"):**

- 试过让胶片列表"填满剩余空间":`ScrollView` 天生贪婪,结果它吃掉整条栏、
  把「相纸」推到最底,**空隙变成夹在两个列表之间** —— 比原来的空白更糟(抓图确认)。
- 最终做法是把列表的**行数**调大:`FilmSection.wellRows` 9 → **20**(原来按图纸是
  9,给出两个分组)。参数搬走后整条左栏只有目录,九行让栏大半是空的、还要滚动才能
  看到本可放下的胶片。
- **残余空白的真因**:982pt 高的栏里两个目录只有约 600pt 内容。要真正填满需要
  **内容**,不是高度 —— 候选是左栏顶部的导航器/预览(缩放取景框)或历史记录。
- **已按此做**:行数调到覆盖整个目录 —— 胶片 `wellRows` 9 → **22**(20 部 + 2 个
  分组标题),相纸 5 → **12**(8 张 + 2 个分组标题 + Positive + 不使用相纸配置);
  并在左栏顶部加 **导航器**(`Panels/Sections/NavigatorSection.swift`):当前帧缩略图
  + 视口矩形 + 缩放读数,空态是「未打开图像」。三块合起来把 982pt 的栏填满。
- **导航器是只读的,并且就保持只读**:它画出视口但不拖动。用户判断"让它真的承担导航
  作用不太有必要";拖动还要写 `renderer.viewport`(Session 只镜像),不划算。
- **导航器的三个比例 bug(2026-09-23 修完)**,根因是同一个:**盒子的形状在布局时
  依赖了还不知道的数据。**
  1. `.frame(maxWidth: .infinity)` 写在 `aspectRatio` 外面 → overlay 量到整栏 254pt
     而照片只有 92pt 宽,视口框横跨整栏。
  2. 把比例改成取自缩略图后更糟:缩略图是**异步**到的,盒子先按兜底 3:2 定型,再把
     竖构图 `.fill` 进去 → 放大并裁切。这就是"比刚才更奇怪了"。
  3. 最终做法**不再推断比例**:固定盒子(满栏宽 × `navigatorHeight`),照片按比例
     **fit** 进盒子(手算 `fitted(_:in:)`,和胶片条的 `aspectRatio(.fit)` 同一套算术),
     视口框画在**照片矩形**的坐标系里。盒子不可能被布局两次,框也不可能和照片不一致 ——
     两者由同一个数算出。竖构图两侧留中性底,是诚实的信箱边。

**一处未做视觉复核**:设置页与缩略图 —— `--snapshot` 只有编辑器与导出页两个开关,
缩略图还需要真实图片(相机 fixtures 不在本机)。这两处的观感要在真窗口里看。
P2 的两栏布局已按 1512×982 抓图复核(左右栏、顶栏文件动作、两栏 section 标题对齐)。

**导出页已按同一规则改完(2026-09-23,第二次视觉检查):** 缩放药丸与计数药丸、
三处输入/下拉胶囊、命名芯片(Orig. Name / Film / Print / Date,按各自底色)、配方列表

**竖分隔线(左右栏↔画布)已改为 `ruleSoft`** —— 用户反馈"分栏中间这个白线太实了"。

### 9.8 应用图标(2026-09-23)

概念图是两卷叠在一起的胶片:后面一卷银色、偏左上,前面一卷橙色、偏右下。实现是
`Spektrafilm/Silverphase.icon` —— 一个 **Icon Composer 文档**(`icon.json` + `Assets/*.svg`),
由 `Tools/make-icon.py` 从一组参数画出两条素材。

**为什么是文档而不是一张 PNG**:macOS 26 起图标的最终样子由系统合成 —— 圆角外壳(遮罩)、
Liquid Glass 的高光与折射、阴影都是系统加的。往 SVG 里烤一层高光,屏幕上就会有两层;所以
素材里**只有材质**:

- **背景**:文档的 `fill` 是一条很浅的渐变(白 → 冷灰)。**dark 外观不写 specialization** ——
  系统自己给深色底,这正是"玻璃由 Apple 自动添加"的同一件事:浅色/深色两种底座都是系统的。
- **两条胶片**:各自一个 **group**(各自一份玻璃与阴影,前面那卷的影子才会落在后面那卷上),
  `glass: true`、`lighting: individual`、`blur-material 0.4`、轻微 `translucency`,
  前面那卷多一个 `refractivity`(要在文档顶部声明 `features: ["refractivity"]`)。
- **齿孔是孔,不是白点**:一条 `fill-rule="evenodd"` 的 path 把外框和 12 个孔放在一起,
  所以背景和玻璃会从孔里透出来。**画格窗是面板**(胶片透明的片基),画在上面。
- **齿孔每边 6 个,不是 35 mm 的 9 个**:16 pt 下 9 个只会连成一条虚线。

**第四个踩到的点,而且它是"图标没换"的元凶**:上一个产品名留下的 `SpektraLab.icns` 不在源码树里、
也不在 `git ls-files` 里,而在**构建中间产物** `DerivedData/…/assetcatalog_output/thinned/`(时间戳
14:09,改名之前那次构建)。actool 的增量构建会把整个 thinned 目录**复制**进 bundle,**连时间戳一起**
—— 所以只从 bundle 里删掉它没用,下一次构建它又回来了,`Contents/Resources/` 里就一直是
"新图标 + 一个旧的 `.icns`"。删要删中间产物那份(或 clean)。**判断"跑的是哪一版"仍然看时间戳**,
但看的是 `Assets.car` 和 `Silverphase.icns` 的,不是"有没有 `SpektraLab.icns`"。

**三个踩到的点,都记在这儿**:

1. **`groups` 的顺序是"前 → 后"**(和 Icon Composer 的图层列表一样,第一行在最前面)。
   把橙色那卷写在前面才压在银色上面 —— 先写银色时渲染出来是反的。
2. **`color-space-for-untagged-svg-colors` 只接受 `display-p3`**(这个 Icon Composer 构建
   会拒收 `srgb`,报 "The data couldn't be read because it isn't in the correct format")。
   于是 SVG 里没标色的十六进制会被当成 **P3 数值**读,而设计是在 sRGB 里选的 —— 直接把 sRGB
   的十六进制写进去,屏幕上每个颜色都会比设计的更艳。所以 `make-icon.py` 把 sRGB 经过
   线性光 + CSS Color 4 的矩阵转成 P3 数值再写文件:sRGB `#FF9F0A`(界面的 accent)
   落到 P3 的 `#F2A33C`,是同一个橙色。
3. **`position` 必须同时给 `scale` 和 `translation-in-points`**,只给 scale 会让 Icon Composer
   打不开文档(而旧 schema 会放它过)。

**"透明叠加"是怎么做出来的(用户三次反馈,从"上面黄的把下面灰的覆盖了"到最后一次"和之前一样",
参照官方照片 App 那朵花瓣)** —— 五件事,每一件都是我一开始做错的:

0. **"透过来"是材质的事,不是把 `glass` 关掉。** 这一条我前后搞错了两次,最后按用户的提醒回去读规范
   才做对:玻璃的**透射**由**组**上的 `translucency` 控制(UI 里叫 Translucency,"content behind
   the glass shows through"),`blur-material` 控制它透过来时**糊不糊**,`refractivity` 是边缘那层
   折射/放大(照片 App 花瓣边上的"透镜"),`specular` 是highlight。正确的组合是:

   | 键 | 值 | 作用 |
   |---|---|---|
   | 层 `glass` | **true**(两卷都开) | 这一层参与 Liquid Glass |
   | 组 `translucency` | 前卷 **0.60**(dark 外观 0.40) | 后面那卷透过来多少 |
   | 组 `blur-material` | 前卷 **0** | 0 = 透过来是**清晰**的胶片,不是磨砂玻璃 |
   | 组 `refractivity` | `{enabled, strength 0.35, depth 0.30}` | 边缘的透镜感 |
   | 组 `lighting` | `individual` | 每层各自受光 |
   | 素材 alpha | 前卷 **0.96**(窗 0.70) | **只管颜色**,不要拿它当透射 |

   - **我错在哪**:先用整卷 alpha 0.60/0.68/0.75 去做透射 —— 结果是橙色被冲成奶白,而
     透明度并没读出来;然后干脆把前面那卷的 `glass` 关掉(那一版**确实**透,但**没有玻璃质感**,
     用户的反馈:"透是透了,但是没有玻璃质感")。**材质开着才对**,alpha 交给材质。
   - **实测颜色**(白底,以 sRGB 读):`#F89D13` —— Apple 橙是 `#FF9F0A`,差 2/2/9,已是同一条橙。
   - **dark 外观必须单独给 `translucency`**(`translucency-specializations`,整个对象替换):
     0.75 的透射在近黑底上会把橙卷压成褐色;dark 用 0.40,灰卷依然透得出来。
   - **透射也不能给太多**:0.75 + refractivity 0.5 在 1024 尺寸下会把橙卷下半段冲成奶白
     (白底从那里透上来),最后落在 **0.60 / 0.35** —— 橙卷保住自己的橙,灰卷照样透得出来。
     这两个数就是最后的旋钮。
1. **"透明"也可以是形状上的开口。** 这是最后一层、也是最关键的一层:把画格窗
   做成 alpha 很低的**填充**(0.18)时,系统仍然把它**填成一块玻璃** —— 于是"透过去"看起来只是
   "变淡",而不是"看见后面那卷"。只有把窗做成**真正的开口**(和齿孔一样进 `evenodd` 那条 path,
   那里根本没有面积),后面那卷才会 **100% 透出来**。所以现在:**橙卷的边框是不透明的 Apple 橙,
   画格窗是三个洞**;银卷的窗仍是浅灰面板(胶片片基),孔也是洞。这也是物理上对的 ——
   画格窗本来就是片基露出来的地方。
2. **每一卷是"半透明的彩色形状",不是"不透明的形状加一层雾"**。花瓣那种观感 =
   颜色本身带 alpha(底色上偏粉彩、两个形状交叠处变深),而不是把整组的 `translucency` 拉高
   —— 后者只会把橙色冲成奶白(试过 0.6/0.75/0.9,一路变浑浊)。现在素材最外层是一个
   `<g opacity>`(前面那卷 0.96、后面 0.94)。**整卷压到 0.68 会把橙色冲成奶白** —— 0.60/0.68/0.75
   三档都试过,越透越不像 Apple 橙;所以 alpha 只留一点点材料感,"透"交给第 0 条的开口。
   - **实测**:`<g opacity="0.68">` 与 `opacity="1.00"` 两张渲染 psnr 28.65 —— 组的 `opacity`
     是被认的;而最初把 alpha 写在渐变路径的 `fill-opacity` 上,画面上**看不出任何变化**,
     所以现在一律写在组和渐变的 `stop-opacity` 上。
3. **后面那卷必须是一块灰板,不是"白底加灰框"**。一开始银色那卷的窗是接近白的(#E8EDF4),
   于是前面那卷底下几乎全是亮的 —— **没有东西可以透**。概念图里灰卷是一整块灰、只有齿孔是
   白的,所以现在银色卷的窗只比片身亮一点点(#B4BFCB 对 #C2CAD6→#7C8797),齿孔仍然是真孔。
   这时候橙色压过去才会明显地变灰、变深,而齿孔透出来是亮点。
4. **两卷要错开**(见上):窗对窗互相抵消。竖直方向错开接近一个画格间距,前面的窗落在后面的
   片身/齿孔上,叠加才读得出来。

**`blend-mode` 在 Liquid Glass 层上是失效的**:去掉前面那层的 `blend-mode: "multiply"` 再渲染,
PNG **逐位相同**(psnr = inf),所以那个键已经从文档里删掉,不留一个看起来在起作用的东西。

**验证**:`ictool`(在 `Icon Composer.app/Contents/Executables/`,注意**不是**
`Developer/usr/bin/ictool`,那是另一个同名工具)渲染 Default/Dark/128 pt 三个 rendition 看效果;
然后构建 app,`Assets.car` + `Silverphase.icns` 进包,再用 `Tools/render-icon.swift` 按 Finder
的方式读回来 —— 那就是 `screenshots/app-icon.png`。**图标编译失败是一句话的构建错误,
图标没进包却是"构建成功"**:所以这一步每次都要做。

### 图标这条路上最贵的一课:缓存骗了两个人

改完素材之后我连着做了四件事,每一件都在"验证",而**四件里有三件读的是缓存**:

1. **`NSWorkspace.icon(forFile:)` 是 `iconservicesagent` 给的,按路径缓存。** 同一个路径反复读,
   拿到的是**几轮之前那次编译**的图标 —— 所以我的"从构建产物读回"证据一直是旧的,而
   `ictool` 直接渲染包一直是对的,两边**长期不一致**,我却用 psnr 去比、还比错了(见第 2 条),
   于是把"包是对的、读回是旧的"误读成"包和构建产物一致"。**判据**:换一个**从未存在过的路径**
   (`ditto` 到 `build/view-<时间戳>/`)再读,或者直接看包里的 `Silverphase.icns`(`sips` 能读)。
   同一个路径删了重建也没用 —— 缓存是按**路径**记的。
2. **不要对两张不同取景的图标做 psnr。** 构建产物里的 rendition 带 macOS 标准的**外边距**
   (824/1024),`ictool --width N` 渲染的是**贴边**的 —— 同一张图 psnr 只有 4.7 dB,
   看起来很"不同",其实一模一样。图标只能**看**,不能这样量。
3. **改目录里的文件不会改目录的 mtime**,而 Xcode 把 `.icon` 当**一个输入**看:于是 asset catalog
   每一步都跑了,图标本身却没重编。`Tools/make-icon.py` 现在写完素材会 `os.utime()` 一下
   包目录 —— 一行,根治。
4. 顺带:`Contents/Resources/` 里那个**上一个产品名的 `.icns`** 来自**中间产物**
   (`assetcatalog_output/thinned/`,actool 每次连时间戳一起复制),删 bundle 里那份没用。

**现在这份图标的样子**(以 sRGB 读):橙卷是一整卷**半透明 Apple 橙**(整卷 alpha 0.85,

### 定案:一卷胶片 = **片基 + 画框**(2026-09-23,最后一版)

用户第三次反馈:"这个透的不太对吧"。这一次不是缓存,是我的模型错了 —— 我把"透"整个交给
**材质透射**,于是白底也从每一处透上来,橙卷下半段被冲成奶白(材质还把灰卷的窗糊成一块)。
物理上没错(半透明的橙色滤片压在白纸上就是发白),但**那不是胶片的样子**。

**一卷胶片其实是两样东西**,现在按这个做:

- **画框**(`2-orange-strip.svg`,层名 "Orange frame",`glass: true`):不透明的 Apple 橙,
  齿孔是孔、**画格窗是开口**。材质给它边缘高光与折射 —— 这是用户要的"玻璃质感"。
- **片基**(`2-orange-strip-base.svg`,层名 "Clear base",`glass: false`):三个画格窗大小的
  **浅橙**块(`#FFB84D`,`opacity 0.55`),画在框后面。它把透过去的灰卷染成胶片的颜色,
  于是窗读起来是"片基"而不是"框上挖的洞"(用户否掉过那个:为什么橙色只剩下外框了)。

于是组上的 `translucency` 不再承担"透",退回**0.25**(dark 0.20)只留一点材料感;
`blur-material: 0` 让透过去的东西保持清晰;`refractivity 0.35/0.30` 是窗边的透镜。

**实测(sRGB,白底)**:框 `#FC9C0A` / `#F19313` —— Apple 橙是 `#FF9F0A`,同一条橙;
窗内(灰卷处) `#F2CC92`,灰卷的身、窗、孔都还看得见。

**两个旋钮**:`Tools/make-icon.py` 里 `ORANGE` 的 `base`/`base_alpha`(片基的颜色与浓度)
与 `icon.json` 里那组的 `translucency`。用户最后定的是 `base_alpha = 0.75`
(0.55 偏淡、0.90 层次没了;窗内实测 `#F8C374`,画框 `#FC9C0A`)。

**图标缓存有两层,杀 agent 不够**:`iconservicesagent` 的**按路径**缓存之外,磁盘上还有
`~/Library/Caches/com.apple.iconservices.store` 与 `/private/var/folders/<...>/C/com.apple.iconservicesagent`。
只 `killall iconservicesagent` 时,重启后的 agent 会把这些 store 读回来,**同一个路径仍然给你几轮前的图**
(用户的 Finder"简介"预览和 Dock 都是这样)。要真刷新:删掉上面两处 store + `killall iconservicesagent`
+ `touch` bundle 目录 + `lsregister -f`,然后重开"简介"窗口。
另外 **bundle 的"修改时间"不会因为里面文件被重写而变**(只有增删文件才变),所以 Finder 显示
"修改时间 22:39"而 `Assets.car` 是 23:01 是正常的 —— 判据看 `Assets.car`/`Silverphase.icns` 的
时间戳,或者把 app `ditto` 到一个新路径读回。

### 深色底是**系统设置**,不是"深色模式"带来的

用户问"按理说符合规范的图标是不是可以变成深色底?" —— 可以,但 macOS 26 里**图标的深色底是一个
独立的设置项**,和"浅色/深色模式"不是一回事:

**系统设置 ▸ 外观 ▸ 图标与小组件样式**(Icon & Widget Style),四选一:**默认 / 深色 / 通透 / 色调**,
后三种还有 **自动 / 始终** 两种(自动 = 跟随系统的浅色/深色)。

- **默认**:图标就按开发者画的样子显示(背景的颜色都在)。**macOS 自带的 App 也一样** ——
  用户截图里深色模式下的 Dock,照片的白色花、访达的蓝白脸都还是原样,就是这个设置停在"默认"。
- **深色**:系统把图标的**背景**去饱和压暗,前景(我们那两卷胶片)保留颜色。
- **通透**:整个图标变成 Liquid Glass,**背景透出桌面壁纸** —— 想要"透明"就是这个,而且是*系统*
  给所有 App 的,不需要 App 做什么。
- **色调**:整体上一个系统色。

**文档这一侧该做的**:把深色底**写出来**(`fill-specializations` 里 `"system-dark"`),
这样"深色"这一档落在一个开发者认可的背景上,而不是让系统去猜 —— 实测写不写它,
`--rendition Dark` 逐位相同(系统本来就会兜底),但文档说了才是一个可复核的意图。

**为什么我之前的"读回"看不到这些档**:`NSWorkspace.icon(forFile:)` 在命令行进程里画的是
**默认外观**,所以从 bundle 读回永远得到浅色那一版 ✗ 它只能证明"图标进包了",
**要比较外观必须用 `ictool --rendition Default|Dark|ClearLight|ClearDark|TintedLight`**。

### 9.9 启动画面(2026-09-23)

**它原来是什么**:360×190 的 `Theme.card` 上一行字、一行 "film simulation"、一个系统 spinner 加一行状态。

**现在**:一张 **360×194 的圆角卡片**,自上而下 —— **Silverphase** 字标(28 pt semibold)、
一行 tagline、**确定进度条**(Apple 橙、纯色,轨道是下沉的 well + 内描边)、底部一行状态 +

**第二版(用户看了真窗口之后的两条)**:① "不用出现图标了…加上图标感觉整个版面太大了" ——
图标拿掉,字标和进度条就是全部信息,卡片因此收小到 360×194;② "顶部那一条黑条也很奇怪,
这里并没有窗口" —— 那是 `.titled` 窗口的**标题栏**:即使 `titlebarAppearsTransparent` +
`fullSizeContentView`,系统仍会在顶部画一条。所以窗口改成 **`.borderless` + 透明背景**,
卡片由视图自己画,复用 `StandaloneWindowSurface`:全局窗口底色 `Theme.windowSurface`,
`modernContainerRadius` 16pt 圆角与共享 1pt 边线,不叠旧卡片底色或顶部渐变。
独立窗口不套编辑器工具层的玻璃背景。无边框窗口 `hasShadow = false`,
投影由共享 `Theme.WindowShadow` 绘制:半径 18pt、向下偏移 8pt。
透明留白每侧为三倍模糊半径加偏移（62pt）,窗口尺寸由卡片和该留白计算,
避免原来每侧只有 14pt 而裁掉阴影;卡片尺寸保持不变。
品牌名、简介、进度条、状态行采用 leading 对齐,共用 `space20` 外边距。
品牌组内部用 `space8`,进度与状态用 `space12`,组间最小 `space20`;
文字字号保留,通过共享 `bootWordmark` / `bootTagline*` 字体角色定义。

**"宁可慢一点"是明确要求,所以有了下限**:`BootWindowController.minimumOnScreen = 2.6 s`。
这是**人为的**,文件头里原来那句"nothing sleeps and nothing is padded"已经改掉并写明原因 ——
本机热启动只要 ~650 ms,不设下限时这个窗口只闪三分之二秒,读不出名字,也就不是品牌时刻。
下限只加在**成功**路径上:失败(能力拒绝)立刻交接,不能把"应用坏了"的解释扣在 logo 后面。
实测时序:`open` 后 0.9–3.3 s 屏幕上**只有**启动画面,3.7 s 出主窗口。

**顺带修掉一个潜伏的 bug**:文件头一直写着"Show it, hide the editor",但代码从来没隐藏过编辑器 ——
交接只要 0.65 s 的时候没人看得见,加了 2.6 s 下限之后,主窗口就明晃晃地停在启动画面后面。
现在 `present` 里隐藏一次,等待期间**每个 tick 再隐藏一次**(SwiftUI 随时可能把它 order in),
交接时只把它拿到最前。

**强调色**:进度条、徽标、失败图标都用 `Theme.accent`(Apple 橙 `#FF9F0A`),和界面一致;
进度条**纯色不渐变**(沿用"橙色不需要渐变了"那条)。tagline 的**字距只在英文里加** ——
中文加字距是每个字之间的缝,读起来像排版事故。

**抓图**:`--boot`(`--boot-phase starting|warming|ready`)渲染这一页,三档各一张,存
`modern_UI/design/snapshots/boot-*.png`。为什么不能用 `screencapture`:它要屏幕录制权限,
这个 harness 没有;而这个窗口的真实生命也只有 2.6 s。文案在字符串表里(`bootTagline` /
`bootStarting` / `bootWarming` / `bootReady`),相位行由 `Session.BootPhase.key` 查表。

`sectionTitle` 12.5 SemiBold、`label` / `listItem` 11 Regular、`chip` 11 Medium、
`value` 11 Medium 等宽数字、`pill` 9.5 Medium —— 冻结在 `eda971b`,理由是
TOKENS-v3 §9 说"在它自己的图纸被翻译之前不要全局重指"。代价是**没有任何文档承认、

而不是改指 —— 别名是第二套刻度长回来的地方。表格行用 `label` / `value`,列表用
`stockItem`,chip 用 `value`。任何视图再伸手要第五档,`ModernCalibrationTests` 会红。

**改掉的四处**:

1. **相机不再有第二套标签密度**(核心那条)。v3 给相机分区一个 **70 pt 的标签列 + 9 pt 的标签**,

   这不是层级,是图纸上两处不同的文字框。九个角色的字重分配本来就是为了让层级由**字重**说,
   不由**字号**说。现在 `SliderMetrics.camera` 这个预设被删掉,相机分行与胶片分行取同一个
   `Theme.Font.label` / `sliderLabelWidth = 84`。代价是相机的控件整体右移 14 pt(图纸里它们在
   x 86.35),换来的是一栏之内只有一条竖直的标签轴。
2. **正片 / 负片 眉标 Regular → Medium**。规则表里它一直是 Medium,代码却是 `body` 的
   Regular,于是列表的分组标题和它下面的胶片条目同重,读完像多了一行条目。
3. **设置 ▸ 诊断的读数**(`readout`):标签留在 `caption`(它说的是那个数,不是控件),**数值**

4. **导出页四处串了刻度**:空态 / "Rendering the preview…" / 空工作列表 / `PillField` 的默认字体

   `Theme.Font.Export.label`,`PillField` 的默认值也一并改掉 —— 它今天的五个调用点都显式传了
   `F.label`,默认值只会害到下一个调用点。

**导出页正文并入编辑器轴(2026-09-26)。** 用户贴出两张截图:"显然还是没有统一规范吧"。

**第二轮:同一个 section 里的三个控件三个尺寸(2026-09-26,用户第二次指出)。**
"位置"区的三行原本是三种写法 —— 手写的 `HStack` 包一个 `PillField`(药丸贴着文字)、

(`maxWidth: .infinity` 撑满)。用户的读法是"三个下拉菜单用了三个尺寸"。修法是把三行
收敛到同一个 row 工厂(`row(_:control:)`),控件统一的宽度、高度、内边距:

- 控件宽度 = 标签列之后剩下的整列(`.frame(maxWidth: .infinity)`),三个都一样;
- 控件高度 = `bodyControlHeight`(= `modernControlHeight` 13.9),药丸不再用图纸的
  `rowHeight - 1`(13.7)而那一个 field 是 22;
- 药丸文字内边距提成一个名字 `PillFieldGeometry.textInset`(9),field 复用它
  (原来是 9 和 8 两个值)。

**并且删掉 `ExportPage` 里所有 `compact ? A : B`。** 窗口和栏是同一页,按家分叉的值
就是"另一套设计"的别名 —— 而且两边各自错向相反:独立窗的表格比自己分区标题右 17 pt,
栏里的行距 6.5 pt 而检查器是 17–20。现在两者读同一组值。

**唯一保留的宽度差异是 `Metric.Export.labelWidth`(68.5)**:编辑器的 84 pt 列加上控件
之后,313 pt 的卡片只剩 209 pt,而四个命名 chips(原文件名 / 胶片 / 相纸 / 日期)需要
208 —— 84 会把 chips 裁掉。**这是宽度决定,不是第二套节奏**:标签的字号是编辑器的,
轴起于 `modernContentInset`,只有列的宽度属于那个窗口。

**一条被记反的规则(2026-09-26,用户澄清)** —— 现代模式**不需要折叠**,这是布局本身
而不是遗漏:右栏一次只显示一个物理阶段,换阶段靠顶栏那排 stage 按钮,所以那里的分区
没有"折起来"这回事。§3.7 的"分区头 = 展开三角 + 标题 +(可选)•••"只适用于**传统栏**。
现代头的结构是**标题 + •••**,`PanelSection` 在 `modernPanelChrome` 下恒定展开、不读
`expanded` —— 不画三角就不该有一个假装存在的折叠状态。独立导出窗同理:它的分区就是
那一页。**不要把这条"修"成读取 `expanded`** —— 那就必须把三角加回来,而现代检查器
不是一摞可以折的东西。`ModernCalibrationTests` 钉住这个缺席。

**核对方法(可重跑)**:把 spektra 目录下每个 `.font(.system(` 的**文本**找出来(留着的只有
关于面板里那段 `.monospaced` 的许可证正文,那是有意的),再找每个没有设字体的 `Text`(剩下的都在
AppKit 菜单与 `.alert` 里,那是系统的字,不该动)。两条命令都干净:

```
grep -rn "\.font(\.system(" Spektrafilm/ | grep -v Image(systemName   # → 只有 AboutWindow 的许可证
grep -rn "\.custom(" Spektrafilm/                                    # → 空
```

**像素证据**(1:1,`--snapshot 1400x900`,右栏裁切):相机与胶片两行**同字不同行**的
`胶片`两字,墨迹框都是 42×22 px,逐像素最大差 3/255、超过阈值 8 的像素 **0 个** ——
同一字号、同一字重、同一字体。标签轴一律起于 x 16 pt;控件区起于 x 100 pt(= 16 + 84),
测光模式的药丸就落在这里。改动后 `LayoutTests`(9 例)与 `PanelResizeWiringTests`(4 例)全绿,
前者有两处断言从"相机另一列"改成"没有哪一栏还是相机那列"。

## 11. 实现约束(SwiftUI / AppKit / Metal)

这一节是**怎么实现**的规范,不是**长什么样**。它合并了 `../UI-GUIDELINE-swiftui.md`
(2026-09-26 删除)里**仍然成立**的部分:§0 的原生约束、§2 的窗口、§3 的分栏、
§4 的色彩规则、§8 的并发、§9 的打包、§11 的诱惑清单。那份文档里描述文件树、
`SplitContainer` 和构建顺序的章节当时就已经过时,不在这里。

### 11.1 这是一台原生 macOS 应用,没有网页

应用以签名的 `.app` 交付。**没有例外地禁止**:HTML/CSS/JS/TS、任何前端框架、
Electron/Tauri/`WKWebView`、webview 里的 canvas、WebGL/WebGPU、Storyboard 与 XIB、
任何跨平台 UI 工具包。

理由不是口味,是三条硬约束:

1. 画布是 Metal 纹理管线,跑 3D LUT 和大图,**必须自己拥有 drawable 和色彩空间**。
   浏览器拿不到一块 `displayP3`/ProPhoto 的 `CAMetalLayer`。
2. 色彩管理是这个产品的全部意义。多一层不可控的色彩变换就多一次 2026 年那次
   双重编码级别的 bug。
3. 蒙版用 `VNGenerateForegroundInstanceMaskRequest`(Vision),网页没有对应物。

渲染引擎是**编译进二进制的 C++**,通过手写的 `extern "C"` 面暴露给 Swift,渲染到
`MTLTexture`。**仓库里没有 Python**:构建期和运行期都没有 `src/`、没有 venv、没有子进程。

### 11.2 窗口与应用

- 一个 `Window`(不是 `WindowGroup`):一次一个会话。第二个窗口意味着第二个会话,
  而那不存在。
- **强制深色**。这是产品决定,不是偏好:浅色 UI 会干扰对影调的判断。
- 用 `@Observable`(Swift Observation),不用 `ObservableObject`。细粒度失效在这里
  是功能:拖一根滑杆不能让胶片条重画。
- 窗口最小 **1100 × 700**。

### 11.3 三栏与折叠

**不要用 `NavigationSplitView`**(它建模的是层级导航,带来侧栏开关动画、窄宽度自动
折叠、`.toolbar` 位置假设)。**不要用 `HSplitView`**(拿不到程序化的分隔位置,
也干净地折不到零)。

实际结构在 `Controls/PanelResize.swift`,三个类型而不是一个:

- `PanelWidthRange` —— 最窄、**标准**、最宽作为一个值,所以一个边界不可能被读出而
  另外两个缺席。`standard` 就是图纸自己的宽度,这让全新安装量出来就是图纸。
- `PanelResizeHandle` —— 抓手,挂在栏的内边缘上做 **overlay**,不做 `HStack` 的兄弟:
  一个 6 pt 的兄弟视图会把画布挤过去 6 pt,让每次截图都移动。
- `PanelWidthStore` —— 宽度,存在自己的命名空间键下,**读取时 clamp**,这样后来收紧
  的范围不可能把栏打开到范围之外。

**必须遵守的几条**(都是踩过的):

- **1 pt 可见分隔线,6 pt 命中区。** 1 pt 点不中,10 pt 难看。
- **`minimumDistance` 要小但不能是 0**(`PanelResizeHandle` 用 1):0 会让"双击恢复
  标准宽度"先被当成一次拖动。
- **拖动开始时捕获起始宽度。** 每帧把 `translation` 累加进 `width` 会复利 —— 栏会从指针
  下面加速跑掉,到了边界两边永久不一致。
- **clamp,永远不让画布到零。** 栏会折,画布不会。
- **不要给拖动加动画。** `width` 上的任何隐式动画都让边缘滞后于光标。
- **折叠可以动画**(0.18 s `.easeOut`),那是一次离散状态变化,不是连续拖动。
- **截图不能继承被拖过的宽度。** 快照模式把两栏都钉在 `standard`,理由和它重置折叠
  标志一样:某人几天前拖宽的栏会静默地成为每一次测量的对象。

### 11.4 画布

**结构**:`Canvas/MetalCanvasView.swift` 包一个 `MTKView`,`isPaused = true` +
`enableSetNeedsDisplay`,只在状态变化、滚动、手势时画。**不要用 display link。**

**色彩规则(不可协商)**,全部来自 `API-SPEC §4` 记录的那次 bug:

1. **永远不要在着色器里套 gamma 曲线。** 引擎的输出已经过 `output_cctf_encoding`。
2. **永远不要用 `_srgb` 像素格式承载已经编码的数据。** 数据已经是编码过的;
   `.rgba16Float` / `.rgba16Unorm` 加上 layer 自己的色彩空间才是对的。
3. **设置 layer 的色彩空间,不要在着色器里转换。** 手动转原色**并且**让 layer 再转一次,
   和 gamma 的双重应用是同一类错误。
4. **Layer 2 的调整刻意作用在编码值上。** 它们是对扫描件的调整,不是物理量。
   不要先线性化 —— 那会让它们变成物理风格的操作,而这正是它们不是的东西。

**工作空间**:整个流程在一个空间里调色 —— **ProPhoto RGB**(会话解析出的
`io.output_color_space`)—— 只在最后按目标转换一次。应用**不实现色彩库**:
每个数都来自引擎烘焙好的色彩数据(适配后的 3×3、CAM16 观察条件常数、C_max 表),
因为第二份传递函数或色域映射就是第二次可能不一致的机会,而不一致看起来像一次调色决定。
`Canvas/ColourManagement.swift` 是应用这一侧;细节见 RFC-018。

**画布上的界面元素**:应用把自己的 chrome 画进纹理(letterbox、蒙版红色)。纹理的
传递函数是 ProPhoto 的 γ1.8,和 sRGB 不同,所以**每一个进入 drawable 的界面字面值都
必须在工作空间里**。RFC-018 之前留在那里的一个 sRGB 灰度,重新编码后带 **1.478×** 的
光量,整个界面会围着照片整体偏移。不需要"改前图"的检查:窗口外边距是一个 AppKit 自己
做色彩管理的 sRGB `CGColor`,画布 letterbox 是着色器过同一 layer 的值 —— 两条路径到
同一个灰,必须落在同一个像素上。

### 11.5 控件

- **`Controls/ScrubSlider.swift` 是唯一的滑杆。** 全应用一个实现,不许出现第二个。
  需求见 §3.1;SwiftUI 的 `Slider` 每一条都不满足。
- **滤镜包滑杆是界面上唯一有颜色的控件**,轨道渐变约 15% 饱和度。
- **只读曲线是"示波器"**:没有控制点、不能拖、不能编辑。
- **系统组件优先**:`Picker`、`Toggle`、`DisclosureGroup`、`LazyVGrid`、`.contextMenu`、
  `.keyboardShortcut`、SF Symbols。不要手画图标 —— `camera`、`film.stack`、
  `plusminus.circle`、`scanner`、`square.and.arrow.down`、`circle.dotted`、`lamp.desk`
  覆盖了这个面板。例外是画出来的原语(选中胶囊、CINE 药丸、滚动条、复选凹槽、
  披露三角),它们没有符号可以代替。
- 纯图标按钮的命中区与字形尺寸由 §2.7.3 规定;**每一个都要有 `.help(...)`**。

### 11.6 胶片条与缩略图

- `LazyHStack` / `LazyVGrid`,500 张图不建 500 个视图。
- 缩略图走 `CGImageSourceCreateThumbnailAtIndex` 或 QuickLook,取**内嵌 JPEG**,
  永不经过引擎;缓存按文件 hash 存 `NSCache`。
- 缩略图生成不在主 actor 上,结果发布回主 actor。
- **格子上没有状态角标。** 选中就是那个框,别的什么都没有(PRD §5)。
- **一个 TIFF 的"缩略图"是第二页,不是 `kCGImageDestinationEmbedThumbnail`。**
  后者对 TIFF 完全没有作用(写出来逐字节相同);而读的一侧失败得很像成功:
  `CGImageSourceCreateThumbnailAtIndex` **找不到**第二页,它返回第 0 页的 2048 px 缩放,
  代价和"没有预览"一样 —— 看上去能用,显示的是错的图,而尺寸断言分辨不出来。
  必须按索引读:`CGImageSourceCreateImageAtIndex(src, 1, nil)`。

### 11.7 调度与并发

- `Session` 与所有视图状态是 `@MainActor`;渲染、Vision、缩略图、引擎调用不是。
- `Renderer` 归主 actor 所有,但它的命令编码跑在 Metal 自己的队列上。
  **不要把它做成 actor**;`MTKViewDelegate` 的回调本来就是串行的。
- **不要在手势处理器的同步路径里 `await`。** 捕获值、起 `Task`、让 UI 从当前状态更新。
- 参数推送由 `Service/RenderScheduler.swift` 合并:防抖(印刷 40 ms / 拍摄 220 ms),
  整个差值发一条,只有 generation 还对上才应用结果。一次拖动产生几次 reprint,
  不是每 tick 一次,过期的回包永远不会覆盖更新的画面。
- 缩放与平移是采样变换(`Canvas/ViewportState.swift`),不重新渲染;≥100% 时采样器是
  nearest,颗粒才读起来是颗粒。

### 11.8 打包

- 引擎的烘焙资源在 `Resources/engine`,**随包走**;`engine/build.sh bundle` 是同步它的
  那一步,`Tools/check-bundle-resources.sh` 在资源或许可证缺失时构建设败。
  静默的失败模式是**陈旧**而不是缺失。
- 许可证不是装饰:包里带着 CC BY-SA 的配置和 GPL 的二进制,`LicensingTests` 断言
  这些文本存在,**并且能从 About 面板用的那个访问器读到**。
- 缓存写在 `~/Library/Caches/<bundle-id>/`,**不要写进包内**(签名后是只读的)。
- Metal 着色器在构建期编译;不要在运行期从源码编译。
